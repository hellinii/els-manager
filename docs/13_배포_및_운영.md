## 1. 목적 및 범위

### 1.1 이 문서가 답하는 것

DOC-001 §10의 **M6(배포·운영)**이 요구하는 다섯이다 — 배포 파이프라인 · 환경 분리 · 로깅 ·
백업 · 보안 처리 방침. 앞의 문서들이 「무엇을 만드는가」를 정했고 이 문서는 **「만든 것이 남의
기계에서 도는 동안 무엇을 지키는가」**를 정한다.

### 1.2 지금 실재하는 것과 예정된 것을 가른다

**이 문서는 P5b 컷 0에 쓰였고 그 시점에 배포는 일어나지 않았다.** 아래 표식을 절마다 붙인다.

| 표식 | 뜻 |
|---|---|
| **실측** | 값을 직접 재서 확인했다. 출처를 함께 적는다 |
| **결정** | 이 문서가 정한다. 코드·설정이 아직 없어도 그 방향으로 만든다 |
| **예정** | 아직 없다. 어느 컷이 만드는지 적는다 |

표식이 없는 서술은 없다. **「대체로 이렇게 한다」를 적지 않는다** — 운영 문서에서 그것은
지켜지지 않는 규약이 되고, 지켜지지 않는 규약은 다음 사람에게 지켜지고 있다는 오해를 준다.

### 1.3 이 문서가 답하지 않는 것

- **시세 공급자 선정** — ADR-007(P5a). 이 문서는 공급자 **0개**를 전제로 배치의 운영만 정한다
- **수집기 구현** — DOC-011 §7.1의 `CronResult` 조립. P5a 컷 3
- **배치의 정체성**(`service_role` 대 전용 서비스 계정) — §11 AQ. **P5a 컷 3에서 닫는다**
- **화면·계약의 내용** — DOC-008·DOC-011

## 2. 환경 분리

### 2.1 표 — ADR-006의 종전 표를 정정한다 *(결정, U-03)*

| 환경 | 용도 | 애플리케이션 | 데이터베이스 | 상태 |
|---|---|---|---|---|
| `production` | 실사용 | Vercel, production branch = `main` | Supabase 운영 프로젝트 (서울 리전) | **예정 — P5b 컷 3** |
| `preview` | — | **자동 배포 비활성** | **없음** | **미구성 (의도된 부재)** |
| `local` | 개발·검증 | `next dev` / `next start`(포트 3100, e2e) | **로컬 Supabase 스택** | 실재 |

### 2.2 `preview`를 세우지 않는 근거 *(결정)*

ADR-006 v0.1은 `preview`를 「PR 단위 검증 · 개발 인스턴스」로 적었다. **그 표는 세 가지를
전제했고 셋 다 성립하지 않는다.**

| 전제 | 실제 |
|---|---|
| preview에 붙일 개발 인스턴스가 있다 | **없다.** 개발 환경은 로컬 Docker 스택이고 그것은 Vercel에서 접근할 수 없다 |
| 두 번째 무료 프로젝트를 만들면 된다 | Supabase Free는 **7일 저활동 시 일시정지**된다(§9). preview 프로젝트는 정의상 저활동이므로 **간헐적으로 죽고 그 상태가 결함처럼 보인다** |
| preview에서 Cron까지 검증할 수 있다 | **불가능하다 — Vercel Cron은 production 배포만 호출한다**(실측, §6.1). 즉 preview 패리티는 애초에 성립하지 않았다 |

**운영 DB에 붙이는 안은 배제한다** — preview URL은 공개이고 쓰기가 운영에 도달한다.

**대신 무엇이 그 자리를 메우는가.** PR 단위 검증의 실체는 **네 스위트**다(`test` · `test:rls` ·
`test:integration` · `test:e2e`). 그중 `test:e2e`는 이미 **프로덕션 빌드**(`next build` +
`next start`)를 띄우므로 「배포된 것과 같은 모드」의 검증은 로컬에 있다. 없는 것은 **플랫폼
자체의 검증**(CDN·리다이렉트·Cron 스케줄러)이고 그것은 preview로도 production 없이는 안 된다.

> **이 절이 남기는 공백을 §11에 등재한다.** 표의 한 행이 비는 것은 판단이지만, 적지 않으면
> 다음 사람이 「preview가 있는데 안 쓴다」로 읽는다.

### 2.3 로컬 환경의 정본 *(실측)*

| 항목 | 값 | 출처 |
|---|---|---|
| API | `http://127.0.0.1:54321` | `supabase/config.toml` `[api].port = 54321` |
| DB | `postgresql://postgres:postgres@127.0.0.1:54322/postgres` | `[db].port = 54322` |
| Studio | `http://127.0.0.1:54323` | `[studio].port = 54323` |
| e2e 서버 | `http://127.0.0.1:3100` | `tests/e2e/helpers/server.ts` `E2E_PORT = 3100` |
| PG 메이저 | `17` | `[db].major_version = 17` |

**로컬 값은 `src/`에 하드코딩되어 있지 않다** — 실측으로 확인했다
(`grep -rn "127\.0\.0\.1\|localhost\|:3000\|54321\|54322" src/` → **0건**). 루프백 리터럴은
테스트 헬퍼와 `config.toml`에만 있다. 그래서 환경 이동이 환경변수 둘로 끝난다(§5).

**그리고 두 테스트 헬퍼가 비루프백 호스트를 거부한다** — `tests/rls/helpers/env.ts`와
`tests/integration/helpers/env.ts`가 `LOOPBACK` 집합을 검사하고 `RLS_ALLOW_REMOTE=1` /
`ITG_ALLOW_REMOTE=1` 없이는 던진다. **즉 스위트를 운영에 겨눌 수 없다.** 그것은 안전장치이면서
동시에 §11에 등재할 공백이다 — 운영의 GRANT를 아무 테스트도 보지 않는다.

## 3. 배포 파이프라인

### 3.1 흐름 *(예정 — 컷 3·7)*

```
로컬 커밋(dev)
  → 스위트 넷 초록 확인
  → main으로 fast-forward 병합
  → git push origin main dev
      ├─ GitHub Actions: lint · typecheck · test        (컷 7)
      └─ Vercel: next build → production 배포            (컷 3)
  → 스키마가 바뀐 경우: supabase db push (수동, §10.2)
  → 설정이 바뀐 경우:   supabase config push (수동·대화형, §4)
```

**두 갈래가 자동이고 둘이 수동인 것이 이 파이프라인의 형태다.** 자동인 것은 **되돌릴 수 있는
것**(빌드·테스트)이고 수동인 것은 **되돌리기 어려운 것**(스키마·플랫폼 설정)이다.

`db push`·`config push`를 CI에 넣지 않는 근거는 §4.4와 §10.2에 각각 적는다.

### 3.2 브랜치 전략과 `phase/*`의 처분

**저장소의 실제 구조 (실측, 2026-07-29):**

```
main                 c6387b8  2026-07-28   ← origin/main · origin/dev와 같다
dev                  c90e563  2026-07-29   ← main보다 20 앞, 0 뒤
phase/p0-scaffold    8ca0d96
phase/p1-calc        ac65221
phase/p2-schema      97eb2a2
phase/p3a-queries    154431f
phase/p3b-mutations  05cc1df
phase/p4-screens     c6387b8   ← main과 같은 커밋
```

**전략 *(결정)*:**

| 브랜치 | 역할 |
|---|---|
| `main` | **Vercel production branch.** 단계가 끝날 때 `dev`에서 **fast-forward**로만 전진한다. `main`에 직접 커밋하지 않는다 |
| `dev` | 작업 브랜치. 컷 단위 커밋이 여기 쌓인다 |

**`main`이 전진하는 순간 그것이 배포 대상이다.** 그래서 병합 전에 **스위트 넷이 전부 초록**이어야
하고, 그 확인이 병합 절차의 일부다(§10.1).

**`phase/*` 여섯의 처분 — 태그로 옮기고 브랜치를 정리한다 *(결정, 예정 — 컷 2)*.**

근거는 실측이다. **여섯 중 둘만 단계 완료 지점을 가리킨다.**

| 브랜치 | 팁 커밋의 정체 | 단계 끝인가 |
|---|---|---|
| `phase/p3a-queries` | `docs: DOC-000 P3a.5 완료 표시 …` | **예** |
| `phase/p3b-mutations` | `docs: P3b.5 완료 반영 …` | **예** |
| `phase/p0-scaffold` | `chore: P0 스캐폴드 …` | 그럴듯하나 미확인 |
| `phase/p1-calc` | `feat(domain): §4.1 적용 쿠폰율 선택 규칙` | **아니다** — P1 중반 |
| `phase/p2-schema` | `feat(domain): 워스트오브 기초자산 0건 거부` | **아니다** — 이름은 스키마인데 **도메인 커밋**이다 |
| `phase/p4-screens` | `feat(app): SCR-201 목록과 SCR-202 상세 (P4 컷 2·3)` | **아니다** — P4는 컷 10까지 갔다 |

즉 「단계별 스냅샷」이라는 주장을 넷이 뒷받침하지 않는다. **그 상태를 「단계별 스냅샷으로
보존한다」고 문서에 적으면 문서가 거짓을 서술한다** — DOC-010 AQ-40이 다루는 「이름이 본문보다
넓다」와 같은 부류다. 그리고 브랜치는 **진행 중인 작업**을 뜻하므로 여섯이 떠 있으면 다음
사람에게 「아직 갈래가 여섯 개」로 읽힌다.

절차 — **순서가 중요하다:**

1. 각 단계의 **진짜 종료 커밋**을 `git log --grep`으로 특정한다(커밋 메시지에 단계·컷이 전부
   적혀 있다 — `(P4b 컷 8)` 등)
2. 주석 태그를 만든다
3. **태그를 먼저 푸시한다**
4. 확인 후 `phase/*`를 로컬·원격에서 지운다

**3이 4보다 앞이어야 커밋이 도달 불가가 되지 않는다.** 4는 원격 변경이므로 실행 직전에 확인을
받는다.

> **채택하지 않은 둘을 남긴다 (U-03의 취지).** (b) 그대로 보존하고 「단계 완료가 아니라
> **마지막으로 푸시된 지점**이다」로 정확히 서술한다 — 가장 싸고 정직하지만 이름이 계속 넓다.
> (c) 스냅샷을 두지 않고 `git log --grep`에만 의존한다 — 되찾을 수는 있으나 조망이 없다.

### 3.3 CI *(예정 — 컷 7)*

| 항목 | 값 |
|---|---|
| 트리거 | `push` · `pull_request` |
| 실행 | `npm ci` → `npm run lint` → `npm run typecheck` → `npm run test` |
| 실행하지 않는 것 | `test:rls` · `test:integration` · `test:e2e` |

**상시 스위트가 CI에서 도는 것은 ADR-003의 배당금이다.** 「`npm run test`는 DB에 접근하지
않는다」를 지킨 덕에 러너에 Docker를 세우지 않고도 786건이 돌아간다.

**인프라 스위트 셋을 넣지 않는 근거:** Docker + `supabase start` + `next build`가 분 단위이고,
`tests/integration/`의 픽스처는 커밋되어 있어 러너마다 `db:reset`을 요구한다. 1인 개발(C-02)
규모에서 그 비용은 로컬 실행으로 감당된다.

> **그러나 이것은 「CI가 초록인데 RLS·계약·e2e는 아무도 안 봤다」를 만든다.** 셋은 여전히
> 손으로 돌려야 하고 그 사실을 잊는 것이 이 파이프라인의 유일한 조용한 실패다. **§11에
> 등재한다.**

## 4. 설정의 정본 — `supabase config push`

### 4.1 무엇이 클라우드로 가는가 *(실측)*

`supabase config push`(CLI **2.109.1**, `package.json` devDependency에 고정)가 로컬
`supabase/config.toml`을 링크된 프로젝트에 밀어 넣는다. CLI 번들 문자열 추출로 확인했다.

| 절 | 클라우드 엔드포인트 | 보내는 필드 |
|---|---|---|
| `[api]` | `PATCH /v1/projects/{ref}/postgrest` | `db_extra_search_path` · `db_schema` · **`max_rows`** · `db_pool` · `db_pool_acquisition_timeout` |
| `[auth]` | `PATCH /v1/projects/{ref}/config/auth` | `site_url` · **`disable_signup = !enable_signup`** · `jwt_exp` · SMTP · rate limit · 비밀번호 정책 등 |
| `[db]` | `PATCH /v1/projects/{ref}/config/database/postgres` | Postgres 설정 |
| `[db.network_restrictions]` · `[db.ssl_enforcement]` | 각각 전용 엔드포인트 | 로컬에서 `enabled = false`면 건너뛴다 |

**즉 저장소의 파일이 클라우드 값의 정본이 된다.** 그것이 §4.2가 AQ-22 R1을 닫는 기전이다.

### 4.2 AQ-22 잔여 R1 종결 — 클라우드 `max_rows`가 저장소에서 온다

**R1의 문언:** 「클라우드 `max_rows`가 저장소에 없어 **운영에서는 여전히 사문화될 수 있다**.
이 단언은 로컬 스택의 **파일**만 본다.」

`config push`가 그 방향을 뒤집는다. 클라우드의 `[api].max_rows`가 `supabase/config.toml`에서
오므로, `tests/db/select.test.ts`의 두 단언이 **운영 값에 대한 진술**이 된다:

```
POSTGREST_MAX_ROWS === configMaxRows()                              (사본의 낡음을 막는다)
APP_MAX_ROWS < TRUNCATION_PROBE_LIMIT ≤ [api].max_rows              (부등호 사슬)
```

형태는 P4b 컷 1·2가 고른 것과 같다 — **값을 맞추는 것이 아니라 관계를 파생시킨다.**

**★ `[remotes.*]`에 `max_rows`를 쓰지 않는다 *(결정)*.** 두 이유가 같은 방향이다.

1. **써야 할 이유가 없다** — 클라우드 값은 로컬과 **같아야** 한다. 다르면 위 부등호 사슬이
   운영에서 깨진다
2. **쓰면 테스트가 빨간불이다 (실측)** — `tests/db/select.test.ts`의 `maxRowsAssignments`가
   **파일 전체**를 `/^\s*max_rows\s*=/`로 스캔하고 「정확히 하나」를 단언한다. `[remotes.prod.api]`
   아래에 한 줄을 더하면 그 전제가 깨진다

**종결의 성격을 정직하게 적는다.** 이것은 **절차적 종결이다** — push 사이의 드리프트(대시보드에서
손으로 고치는 경우)를 상시 스위트가 보지 못한다. 다음 `config push`가 diff로 드러내지만 그것은
배포 시점이다. **그 축을 §11에 새 항목으로 등재한다.**

### 4.3 SEC-03의 클라우드 절반 — 공개 가입 차단

`[auth].enable_signup = false`(`config.toml:184`)는 지금까지 **로컬 설정이고 로컬 프로브만
있었다** — `tests/integration/global-setup.ts`가 로컬 API에 `POST /auth/v1/signup`을 던져
열려 있으면 실패한다.

**클라우드에서 열려 있으면 RLS 정책 32개의 전제가 통째로 무너진다.** DOC-010 §7의 SEC-03 각주가
그것을 실측으로 이미 기록했다 — 뚫었고(가입 → `authenticated` 세션 → `users` 3행 전체 조회),
닫았고, 다시 막힌 것을 확인했다.

**절차 *(결정, 예정 — 컷 3)*:**

1. `config push`가 `disable_signup = true`를 밀어 넣는다(§4.1 — 부호가 반전되는 유일한 필드다)
2. **배포 후 운영 API에 같은 프로브를 던진다** — `POST /auth/v1/signup` → `422 signup_disabled`.
   그 응답을 실측 증거로 남긴다
3. 사용자 추가는 **Dashboard → Authentication → Add user**로만 한다. 트리거가 `public.users`
   행을 만드는 것을 확인한다

> **로컬과 클라우드의 반영 시점이 다르다.** CLAUDE.md와 DOC-010이 적은 「`[auth]`를 바꾸면
> `db:reset`으로는 반영되지 않는다 — `db:stop && db:start`가 필요하다」는 **로컬 경로에만
> 참이다.** `config push`는 클라우드에 즉시 반영된다. 두 절반을 구분해 기억한다.

> **`[auth.email].enable_signup`은 여기서도 건드리지 않는다.** 끄면 GoTrue의
> `EXTERNAL_EMAIL_ENABLED`가 꺼져 **이메일 로그인 자체가** 막힌다(`422 email_provider_disabled`).
> DOC-010 §7 SEC-03 각주의 실측이며 클라우드에서도 같은 매핑이다.

### 4.4 부수 효과 여덟 — `[remotes.production]`으로 가른다

**`config push`는 원하는 둘만 보내지 않는다.** `[auth]` 절 전체가 간다. 밀리는 값을 전수로
세었고 각각을 결정했다.

| `config.toml` | 로컬 값 | 그대로 밀면 운영에서 | 결정 |
|---|---|---|---|
| `:163` `site_url` | `http://127.0.0.1:3000` | 인증 리다이렉트가 로컬을 가리킨다 | **오버라이드** — 운영 도메인 |
| `:167` `additional_redirect_urls` | `https://127.0.0.1:3000` | `uri_allow_list`가 루프백 전용 | **오버라이드**. ★ 로컬 값의 **스킴이 `site_url`과 어긋난 기존 결함**이므로 로컬도 함께 고친다 |

`duplicate project_id for [remotes.a] and [remotes.b]`로 막힌다.

### 4.5 실행 규약 — **`--yes`를 쓰지 않는다** *(결정)*

**근거 *(실측)*:** `config push` 핸들러는 프로젝트의 애드온 목록을 받아
`Enabling <name> will cost you <price>. Keep it enabled?`를 물을 수 있고 **`--yes`는 그것에
예로 답한다.** C-01(무료 티어 내 운영)로 가는 조용한 경로다.

절차: 대화형으로 실행하고 **diff를 읽은 뒤** 승인한다. 증거로 남길 출력 셋 —

```
Loading config override: [remotes.production]
Updating API service with config: [...]        ← 무엇이 바뀌는지
Remote API config is up to date.               ← 재실행 시. 이것이 §4.2 종결의 실측이다
```

**그래서 `config push`를 CI에 넣지 않는다.** 비대화형은 `--yes`를 요구하고 그것이 위 프롬프트를
자동 승인한다. 「매 배포에 클라우드 설정을 재천명한다」는 매력적이지만 **그 대가가 비용 승인의
자동화**다.

### 5.2 읽는 자리를 하나로 유지한다 *(실측 + 결정)*

`src/lib/db/env.ts`가 `src/` 전역에서 **`process.env`를 읽는 유일한 파일**이며 그것이 두 겹으로
고정돼 있다:

- 린트 — `eslint.config.mjs`의 `els/db-layer-values-and-env`가 `src/lib/db/**`에서 `process` 전역과
  `process.env` 멤버 접근을 금지한다(예외는 `env.ts` 하나)
- 테스트 — `tests/db/no-service-role.test.ts`가 `process.env`를 담은 파일 목록이 **정확히**
  `['src/lib/db/env.ts']`임을 단언한다

**`CRON_SECRET`도 `env.ts`에서 읽는다** — 새 리더를 만들지 않는다. 부재와 **빈 문자열을 함께
던진다**(기존 `require_`의 규약). 비밀에서 이 구분이 특히 중요하다: 빈 값이면 `Bearer `로
시작하는 모든 헤더가 일치한다.

> **함정 하나 *(실측)*.** 위 테스트는 주석을 제거하되 **문자열 리터럴은 보존한다.** 그래서
> 오류 메시지에 `process.env`라는 **문구**를 쓰면 그 단언이 깨진다. 기존 `env.ts`의 메시지가
> 그 표현을 피하는 것은 우연이 아니다.

### 5.3 저장소에 넣지 않는 것

`.gitignore`가 `.env*`를 무시하고 `!.env.example`만 예외로 둔다 — 그래서 새 비밀 파일
(`.env.backup`, §8)은 **자동으로** 무시된다. 규율이 아니라 구조다.

**★ 저장소가 공개다 *(실측: `api.github.com/repos/hellinii/els-manager` → `"private": false`)*.**
그 사실이 §8의 백업 목적지를 결정한다.

## 6. Cron 운영

### 6.1 플랫폼 실측 — 다섯이 설계를 정한다

| # | 실측 | 출처 | 결과 |
|---|---|---|---|
| ① | **호출은 `GET`이다** — 「To trigger a cron job, Vercel makes an HTTP **GET** request to your project's **production deployment** URL」 | vercel.com/docs/cron-jobs | DOC-011 §7.1의 `POST`가 성립하지 않는다 → **`GET`으로 정정했다**(§7.1 U-03). 그리고 **production만 호출하므로** §2.2의 preview 패리티가 애초에 없었다 |
| ② | **타임존은 항상 UTC** | 같음 | 스케줄 값을 KST로 적을 수 없다. §6.2의 환산이 문서에 남아야 한다 |
| ③ | **Hobby는 일 1회 · 정밀도 ±59분** — `0 5 * * *`은 05:00~05:59 사이에 발화한다. 더 잦은 표현식은 **배포가 실패한다** | cron-jobs/usage-and-pricing | 「일 1회」가 선택이 아니라 제약이다. 그리고 §6.2의 시각에 **한 시간 여유**가 필요하다 |
| ④ | **재시도 없음. 배달은 best-effort로 누락도 중복도 가능** | cron-jobs/manage-cron-jobs | **CR-03의 멱등성이 선택이 아니다.** 그리고 「하루 빠졌다」가 정상 범위이므로 감지가 실행 기록이 아니라 데이터여야 한다(§7) |
| ⑤ | **리다이렉트를 따라가지 않는다. 3xx·캐시 응답은 로그에도 남지 않는다** | 같음 | `src/proxy.ts`의 `api/cron` 매처 제외가 **운영에서 하중 부담 부품**이 된다. 307이면 잡이 조용히 끝나고 흔적도 없다 |

부수 실측 — UA는 `vercel-cron/1.0`, 헤더 `x-vercel-cron-schedule`에 발화한 표현식이 담긴다.
Hobby 함수는 `maxDuration` **300초가 기본이자 최대**이고 2GB/1vCPU다.

### 6.2 스케줄 — 값과 근거 *(결정)*

| 항목 | 값 |
|---|---|
| 표현식 | `0 5 * * *` (**UTC**) |
| 실제 발화 구간 | 05:00~05:59 UTC = **14:00~14:59 KST** |
| 리전 | `icn1`(서울) — 운영 DB와 같은 리전 |

> **이 표가 `vercel.json`의 정본이다 *(컷 1)*.** 두 값(`crons[0].schedule`·`regions`)을
> `tests/app/invalidation.test.ts`가 **이 표를 파싱해** 대조한다 — 설정이 문서를 따르는
> 방향이며, 그래야 아래 근거가 값의 출처로 남는다. 백틱을 벗기면 파서가 그 행을 찾지 못한다.

**근거 — 이 시각은 어느 거래소 마감도 겨냥하지 않는다. 공급자의 게시 시각을 겨냥한다.**

채택 예정 공급자(`data.go.kr`, ADR-007)는 종가를 **「기준일자로부터 영업일 하루 뒤 오후 1시
이후」**에 게시한다. 즉 배치가 넣는 것은 오늘 종가가 아니라 **직전 영업일 종가**다. 13:00 KST +
한 시간 여유(실측 ③의 ±59분) = 14:00 KST가 그래서 나온 값이다.

**따라오는 셋:**

1. **`as_of_date`는 `today()`가 아니라 공급자가 준 날짜다.** 배치가 `today()`를 쓰면 전일 종가가
   오늘 날짜로 저장되고 그것이 **형식은 정상이고 값만 거짓**인 상태다. ADR-004 보정이 반환에
   `asOfDate`를 넣는 이유가 정확히 이것이다(P5a)
2. **`isStale`(5일)이 상시 1~3일 뒤처진 상태로 돈다.** 정상이며 결함이 아니다
3. **V-17(미래 일자 거부)은 자동으로 만족된다**

> **★ 당일 종가를 주는 공급자를 붙이는 날 이 시각은 틀린다.** 14:00 KST는 KRX(15:30) ·
> TSE(15:00 JST) · HKEX(16:00 HKT) 마감 **전**이고 미국 세션은 전날 것이다. 그런 공급자를
> 추가하면 스케줄과 `as_of_date` 규칙을 **함께** 다시 정해야 한다. 이 각주가 그때의 신호다.

> **주말·휴장일에도 발화한다.** 표현식에 요일 가드가 없다. 그날은 공급자가 데이터를 주지 않으므로
> `failed[].reason = 데이터 없음`이 되고(DOC-011 §7.1 CR-02) 원장은 오염되지 않는다. 대가는
> 무료 한도의 소비뿐이며 일 10,000회 한도에서 무의미하다.

### 6.3 인증 *(결정)*

| 항목 | 내용 |
|---|---|
| 헤더 | `Authorization: Bearer <CRON_SECRET>` |
| 발신 | **Vercel이 자동으로 붙인다** — `CRON_SECRET` 환경변수가 있으면 cron 호출에 이 헤더를 실는다(플랫폼 동작) |
| 값 | 16자 이상 난수. **ASCII여야 한다** — 아래 각주 *(실측)* |
| 판정 | DOC-011 §7.1 CR-01(불일치 → 401) · **CR-06**(미설정 → 500) |

**미설정을 401이 아니라 500으로 답하는 근거는 §7.1 CR-06에 있다** — 「비밀이 없다」(배포 결함)와
「토큰이 틀리다」(외부 호출)가 같게 보이면 조치가 갈리지 않는다.

> **★ 값은 ASCII여야 한다 *(실측, 컷 1)*.** HTTP 헤더 값은 ByteString(latin1)이므로 비ASCII
> 문자가 들어가면 **요청이 만들어지지도 않는다** — 컷 1의 e2e 초안이 한글 토큰을 보내려다
> `TypeError: Cannot convert argument to a ByteString because the character at index 7 has a
> value of 53952 which is greater than 255`로 죽었다. 즉 비ASCII 비밀의 증상은 401이 아니라
> **호출자 쪽의 예외**이고, 그러면 Vercel 로그에 요청 자체가 남지 않아 CR-06·CR-01 어느
> 갈래로도 보이지 않는다. Vercel이 생성해 주는 값은 ASCII이므로 이 제약은 **손으로 값을 정할
> 때만** 문제가 된다(컷 3).

### 6.4 공급자 0개인 동안의 상태 *(결정)*

**배포 첫날부터 P5a가 공급자를 등록할 때까지 Cron은 매일 503으로 끝난다**(DOC-011 §7.1 CR-07).
200 + 빈 `CronResult`로 답하면 「할 일이 없었다」와 「공급자가 없다」가 같게 보이므로 그 선택은
배제했다.

**이것은 R-05(「각 단계에서 사용 가능한 상태 유지」)의 의도된 이탈이다.** 저장소에서 처음으로
「동작하는 상태」가 **설계상 빨간** 것이므로 그 사실을 여기 적는다. 이탈을 허용하는 근거 둘 —
ⓐ 앱 자체는 완전히 동작한다(시세 수동 입력이 설계된 정상 경로다) ⓑ 빨간 것이 **정확한 상태
보고**이고, 초록으로 위장하면 P5a가 끝난 뒤에도 그것이 도는지 알 수 없다.

> **부작용 하나를 §9에 연결한다 — 503 경로는 DB를 건드리지 않는다.** 즉 Cron이 매일 돌아도
> Supabase 프로젝트의 활동은 0이고, 사람의 접속이 7일 없으면 일시정지된다.

## 7. 로깅 · 관측

### 7.1 CR-04를 재정의한다 — 감지와 진단을 가른다 *(결정, U-03)*

**종전 문언:** DOC-011 §7.1 CR-04 「결과를 로깅한다. 무음 실패를 만들지 않음」.

**그것이 이 플랫폼에서 성립하지 않는다 *(실측)*:**

| 실측 | 출처 |
|---|---|
| **Hobby 런타임 로그 보존 = 1시간** | vercel.com/docs/logs/runtime — Limits 표(Hobby 1 hour / Pro 1 day / Enterprise 3 days) |
| Cron 정밀도 ±59분 | §6.1 ③ |

일 1회 배치의 `console.log`는 **다음에 볼 때 이미 사라져 있다.** 그리고 ±59분이라 「예정 시각
직후에 확인」도 성립하지 않는다. **즉 종전 문언대로면 CR-04는 배포 첫날부터 사문화다.**

**목적을 둘로 가르면 하나는 이미 영속적이고 하나는 요청 시점에 만들 수 있다.**

| | 무엇으로 | 왜 성립하는가 |
|---|---|---|
| **감지** — 배치가 조용히 죽은 것을 알아챈다 | SCR-302의 `isStale`(5일) · `as_of_date` · `source` | **영속적이고 이미 구현돼 있다.** 시세가 낡으면 화면이 말한다. 그것이 배치 실패의 사용자 표면이다 |
| **진단** — 무엇이 왜 실패했는지 본다 | **멱등성(CR-03)을 이용한 재호출.** `curl -H "Authorization: Bearer $CRON_SECRET" <도메인>/api/cron/prices`가 `CronResult`를 **응답 본문**으로 준다 | **보존 기간과 무관하다.** 건너뛴 자산은 `skipped`로 세어지므로 재호출이 상태를 바꾸지 않는다 |
| **전면 실패** | **비2xx 응답** | Vercel Cron 설정 화면의 마지막 실행 상태로 남는다 — 로그와 **다른 보존 정책**이다 |

**`console.log`는 그대로 남긴다** — 1시간 안에 보면 유용하고 비용이 0이다. 다만 **그것이 CR-04를
성립시키는 수단이 아니라는 것**을 §7.1에 적었다.

### 7.2 잔여 — 지나간 중간 실패는 복원할 수 없다

재호출은 **「지금」**을 알려 주고 **「그때」**를 알려 주지 않는다. 어제 배치가 자산 3건에 실패했고
오늘 성공했다면 그 3건이 무엇이었는지 알 방법이 없다.

**종결 후보: `cron_runs` 테이블.** 배치 결과를 DB에 영속화하면 관측이 진짜로 남고 앱 안에서
읽을 수 있다. **지금 만들지 않는 근거:** DOC-002 §3의 테이블 **12 → 13**이 카탈로그 테스트(정확한
목록 대조) · RLS · GRANT · DOC-010 §7 권한 표 · 배치의 INSERT 권한을 함께 끌고 온다. 문서 선행이
필요한 별개의 결정이다. **§11에 등재한다.**

### 7.3 관측 가능한 것과 그렇지 않은 것

| 대상 | 수단 | 보존 |
|---|---|---|
| Cron 실행 여부·상태 코드 | Vercel Settings → Cron Jobs | 마지막 실행 |
| 함수 로그(`console.*`) | Vercel Logs (`requestPath:/api/cron/prices`) | **1시간** |
| 빌드 로그 | Vercel Deployments | 배포 단위로 보존 |
| 시세의 최신성 | **SCR-302** (`as_of_date` · `isStale` · `source`) | **영속** |
| 데이터 정합성 결함 | SCR-302의 ST-06 표식 | 영속 |
| DB 지표·느린 질의 | Supabase Dashboard → Reports | 플랫폼 정책 |

**Log Drain은 Hobby 밖이고 외부 모니터링 도구(Sentry 등)는 도입하지 않는다** — C-01·C-02
판단이 따로 필요하며, §7.1의 재정의가 그 자리를 대신한다.

## 8. 백업 · 복구 — AQ-04 종결

### 8.1 제약 세 개가 수단을 정한다 *(실측)*

| 실측 | 출처 | 결과 |
|---|---|---|
| **Supabase Free는 자동 백업이 없다** — 「Database backups are not available for download for Free Plan projects」. 일 백업은 Pro 이상의 기능이다 | supabase.com/docs/guides/platform/backups · going-into-prod | 백업은 **자가 관리**다. AQ-04의 답이 「주기」가 아니라 **「수단부터」**인 이유 |
| **직결(`db.<ref>.supabase.co:5432`)은 IPv6 전용** | database/connecting-to-postgres | `pg_dump`는 **Supavisor 세션 모드(pooler:5432)**를 지나야 한다. 트랜잭션 모드(6543)는 prepared statement를 지원하지 않아 쓸 수 없다 |
| **저장소가 공개다** (`"private": false`) | GitHub API | 덤프를 **저장소에 커밋할 수 없다.** 공개 저장소의 Actions 아티팩트도 누구나 내려받으므로 그것도 안 된다 — Supabase 공식 워크플로는 덤프를 저장소에 커밋하며 그 문서 자체가 「**Never backup your data to a public repository**」라고 적는다 |

### 8.2 결정 — 로컬 스케줄 덤프 *(결정, 예정 — 컷 6)*

| 항목 | 값 |
|---|---|
| 수단 | `npm run db:dump` — `supabase db dump` **3종**(`--role-only` / 스키마 / `--data-only --use-copy`) |
| 접속 | Supavisor **세션 모드**(`pooler:5432`) |
| 비밀 | `.env.backup` (`.gitignore`의 `.env*`가 이미 덮는다, §5.3) |
| 목적지 | **저장소 밖** — `~/els-manager-backups/YYYY-MM-DD/` |
| **주기** | **주 1회** (launchd, `~/Library/LaunchAgents/`) |
| 보존 | 최근 8주 |

**주 1회의 근거.** A-01 규모에서 데이터 변경이 월 단위다 — ELS 등록은 신규 매수 시점(연 수 회),
상환은 평가일(분기), 시세 수동 입력은 통지 시점이다. 손실 상한은 **「지난 덤프 이후의 손 입력」**
이며 주 단위에서 그것은 최대 몇 건이다. 그리고 `numeric` 값의 정본이 증권사 통지에 있으므로
(A-04) 재입력이 가능하다.

**목적지를 저장소 밖에 두는 것이 규율이 아니라 구조여야 한다** — 안에 두면 `.gitignore`에
의존하게 되고, 그 한 줄이 지워지는 날 금융 데이터가 공개 저장소로 간다.

### 8.3 복구를 실측하는 것이 이 항목의 종결 조건 *(결정)*

**복구해 보지 않은 백업은 백업이 아니다.** 컷 6은 다음을 하고 나서야 끝난다:

1. 로컬 스택을 비운다
2. 3종을 순서대로(roles → schema → data) 되살린다
3. **테이블별 행 수를 원본과 대조한다**

이 대조표가 AQ-04 종결의 증거다.

### 8.4 이 백업이 덮지 않는 것

**실수 복구는 덮고 재해 복구는 덮지 않는다.** 근거 둘 — ⓐ 기계가 꺼져 있으면 안 돈다(launchd는
로그인 세션에 묶인다) ⓑ **오프사이트 사본이 없다.** 기계와 백업이 같은 장소에 있다.

오프사이트를 얻는 값은 「비공개 저장소를 하나 더 만들고 DB 접속 문자열을 GitHub Secrets에 넣는
것」이며 지금 그 교환을 하지 않는다 — 비밀이 기계를 떠나지 않는 것이 이 규모에서 더 값어치가
있다고 판단한다. **§11에 등재한다.**

## 10. 운영 절차

### 10.1 배포 *(결정)*

```bash
# dev에서
npm run lint && npm run typecheck && npm run test
npm run db:reset && npm run test:rls
npm run test:integration
npm run test:e2e
npm run db:reset                 # 통합 픽스처 정리

git switch main && git merge --ff-only dev
git push origin main dev         # ★ push가 없으면 배포되지 않는다
git switch dev
```

**`--ff-only`가 규약이다.** `main`에 직접 커밋하지 않으므로 fast-forward가 아닌 상태는 무언가
잘못됐다는 신호이며, 그때 병합 커밋을 만들어 덮는 것이 아니라 원인을 본다.

**`git push`를 빠뜨리면 아무 일도 일어나지 않는다** — Vercel은 GitHub에서 배포한다. 로컬 병합만
하고 「배포했다」고 생각하는 것이 이 절차의 유일한 조용한 실패다.

### 10.2 스키마 배포 *(결정)*

```bash
npx supabase db push       # migrations/만 적용된다
```

**`seed/`는 적용되지 않는다** — `supabase/config.toml`의 주석이 그것을 명시한다.
그래서 **운영에는 사용자가 시드로 생기지 않는다**(§10.3).

**CI에 넣지 않는다.** 스키마 변경은 되돌리기 어렵고, `db push`는 적용 전 목록을 보여 주므로
사람이 읽는 것이 방어의 일부다. 그리고 마이그레이션 절차(CLAUDE.md)가 `db:types` 재생성을
요구하는데 그것은 로컬 작업이다.

**타입 재생성이 no-op인 마이그레이션이 있다** — GRANT·REVOKE만 바꾸는 것이 그렇다. 그때
`db:types`가 아무것도 바꾸지 않는 것은 정상이며 **「타입이 안 바뀌었으니 마이그레이션이 안
돌았다」로 읽지 않는다.** 커밋 메시지에 그 판단을 적는다.

### 10.3 사용자 초대 *(결정 — SEC-03·A-05)*

공개 가입은 닫혀 있다(§4.3). 사용자 추가 경로는 **하나**다:

1. Supabase Dashboard → Authentication → **Add user**
2. 이메일·초기 비밀번호를 당사자에게 직접 전달
3. `select id, display_name from users`로 트리거가 프로필 행을 만든 것을 확인
4. 당사자가 로그인 후 표시명을 확인한다

> **`auth.users`에 SQL로 직접 넣지 않는다.** 토큰 열 8개를 `''`로 명시하지 않으면 GoTrue가
> 널 불가 `string`으로 스캔해 로그인이 500으로 죽는다(`supabase/seed/00_rls_test_users.sql`의
> 주석에 실측이 있다). Dashboard는 그 처리를 대신한다. **시드 파일의 방식은 로컬 전용이다.**

### 10.4 설정 변경 *(결정)*

`supabase/config.toml`을 고친 뒤 **양쪽을 따로 반영한다.**

| 대상 | 명령 | 주의 |
|---|---|---|
| 로컬 | `npm run db:stop && npm run db:start` | `[auth]`·`[api]`는 `db:reset`으로 반영되지 않는다 |
| 클라우드 | `npx supabase config push` (**`--yes` 없이**) | 즉시 반영된다. §4.4의 부수 효과 여덟을 매번 확인한다 |

### 10.5 커스텀 도메인을 붙이는 날

지금은 `*.vercel.app` 기본 도메인을 쓴다. 붙이면 **셋을 다시 지나야 한다** —
`[remotes.production.auth].site_url` · `additional_redirect_urls` · `config push`.
적어 두지 않으면 도메인만 바꾸고 인증 리다이렉트가 옛 주소를 가리킨다.

### 10.6 되돌리기

| 상황 | 수단 |
|---|---|
| 애플리케이션 결함 | Vercel **Instant Rollback**. ★ **활성 Cron 잡은 롤백되지 않는다**(실측 — 「active cron jobs will not be updated」). 수동으로 끄거나 갱신한다 |
| 스키마 결함 | 되돌리는 마이그레이션을 **새로 쓴다.** `db push`에 되돌리기가 없다 |
| 데이터 손상 | §8의 덤프에서 복구. 손실 상한은 지난 덤프 이후 |
| 설정 오적용 | `config.toml`을 고쳐 `config push` 재실행 |

## 11. 미결정 사항

**번호는 DOC-010·DOC-011과 공유하는 단일 AQ 네임스페이스를 쓴다.** P4b 컷 8이 AQ-41을
소비했으므로 **P5b가 신설하는 것은 AQ-42부터**이며, 등재는 각 항목을 만든 컷과 같은 커밋에서
한다(DOC-000 §4의 각주가 요구하는 규율). **아래는 컷 0 시점의 예정 목록이며 실제 번호 부여는
컷 9(P5b.5)가 한다.**

| 예정 | 항목 | 성격 |
|---|---|---|
| — | **클라우드 설정의 push 간 드리프트를 상시 스위트가 보지 못한다** | AQ-22 R1의 새 잔여(§4.2). 종결 후보는 `count: 'exact'`(AQ-09와 함께) 또는 Management API 조회 스크립트 |
| — | **CR-04의 지나간 중간 실패를 사후 진단할 수 없다** | §7.2. 후보 `cron_runs` 테이블 |
| — | **`preview` 환경 미구성** | §2.2. ADR-006 표의 한 행이 비었다 |
| — | **인프라 스위트 셋이 CI에 없다** | §3.3 |
| — | **Supabase Free 7일 일시정지** | §9. 공급자 0개 동안 Cron이 DB를 건드리지 않는다 |
| — | **백업이 기계 가동에 의존하고 오프사이트 사본이 없다** | §8.4. 실수 복구만 덮는다 |
| — | **배치의 정체성** — `service_role`인가 전용 서비스 계정 사용자인가 | 아래 별항 |
| — | **클라우드의 GRANT를 아무 테스트도 보지 않는다** | §2.3. 권한 매트릭스는 로컬 DB에 대한 진술이다 |

### 배치의 정체성 — P5a 컷 3에서 닫는다

**이 문서는 결정하지 않고 근거만 기록한다.** 문서화된 설계는 「배치가 `service_role`로 돈다」이고
그 사슬이 다섯 곳에 있다(`rls_policies.sql`의 GRANT 주석 · DOC-010 §7.2 · DOC-010 AQ-11 ·
`.env.example` · `tests/db/no-service-role.test.ts`의 예외 근거).

**그런데 두 가드가 상호배타적이다 *(실측)*:**

- `src/app/**`는 `@supabase/*`를 import할 수 없다(`eslint.config.mjs`의 `els/no-supabase-in-ui`)
- `src/lib/db/**`는 `service_role` 문자열을 담을 수 없다(`no-service-role.test.ts`)
- `SUPABASE_SECRET_KEY`라는 **이름**은 `src/app/api/cron/**` 밖에서 금지되고, `process.env`는
  `env.ts`에서만 읽을 수 있다 — **그 두 단언의 교집합이 비어 있다**

**대안이 이미 존재하고 새로 만들 것이 없다 *(실측)*:** `asset_prices`는 `authenticated`에
`arw`(INSERT/SELECT/UPDATE), `asset_provider_symbols`는 `r`(SELECT)이고 정책이 `using (true)`이며
`createTokenClient(token)`이 이미 있다. **전용 GoTrue 서비스 계정 사용자** 하나면 배치가 RLS
안에서, 우회 없이, `SUPABASE_SECRET_KEY` 없이, cron 예외 없이 정확히 필요한 권한만 갖는다.

**갈래 셋:** ⓐ 서비스 계정 사용자 — 예외 자체가 불필요해지고 `ALLOWED_PREFIXES`를 **좁힌다**
ⓑ `env.ts`가 이름을 인자로 받는 리더를 노출 — 감사 지점은 하나로 남지만 **변수 집합을 그 파일에서
읽을 수 없게 된다** ⓒ `ALLOWED_PREFIXES` 확대 — 그 파일의 주석과 DOC-010 §7.2가 명시적으로
금지한다. **ⓑ·ⓒ는 DOC-010 AQ-38이 「단언 4의 정확 일치」에 의존해 세운 논거도 함께 무너뜨린다.**

**권고는 ⓐ다.** 그리고 **P5b 컷 2의 「`service_role` 0 DML」은 어느 답에서도 옳은 바닥이다** —
ⓐ면 영구 상태이고, ⓑ·ⓒ면 P5a 컷 4가 필요분만 올려 주는 출발점이다.
