## 1. 목적 및 적용 범위

본 문서는 시스템이 수행하는 모든 도메인 계산의 알고리즘을 정의한다. 조건 판정, 수령액 산출, 과세 금융소득 산정, 금융소득종합과세, 건강보험료, 연도별 집계를 다룬다.

**본 문서는 알고리즘을 정의하며 상수값을 정의하지 않는다.** 세율·요율 등 법령 기반 상수는 `tax_constants` / `tax_brackets`에 연도별로 저장된다(DOC-002 M-05). 본문에 등장하는 구체적 수치는 2026년 기준 예시이며, 구현 시 상수를 하드코딩해서는 안 된다.

10장의 검증 케이스는 **회귀 테스트로 고정한다**(K-08). 계산 로직 변경 시 해당 케이스가 모두 통과해야 한다.

> **면책:** 본 시스템의 세액 산출은 추정·계획 목적이며 세무 신고 자료가 아니다(DOC-001 C-04).

### 3.1 워스트오브 (Worst-of)

기초자산 중 기준가 대비 등락률이 가장 낮은 자산의 비율.

```
W = min( currentPrice(a) / basePrice(a) )   for a in underlyings(els)
```

**전제**

- `currentPrice`는 **기준일(`asOf`) 이하의 `as_of_date` 중 가장 큰 행**의 값이다. 상한이 없으면 미래 일자 시세로 현재의 조건을 판정한다 — DOC-011 V-17이 그 입력을 거부하나 계약 계층 한 층뿐이므로(DB `CHECK`로 표현 불가) 판정 쪽에서도 상한을 둔다. 판정의 다른 입력(평가일 경과·D-Day·귀속연도)이 모두 기준일에 종속되므로 시세만 벽시계를 따르면 한 화면에 두 시점이 섞인다.
- 기준가와 현재가는 동일 통화이므로 비율 계산에서 통화가 상쇄된다. 환율 변환은 수행하지 않는다(DOC-002 D-03). **상품 통화가 달러여도 같다** *(v1.4)* — 판정은 기초자산 통화 안에서 끝나고 상품 통화와 무관하다(DOC-005 §8.11). 추정 환율(§4.8)은 판정의 입력이 아니며, 환율이 없어도(E-09) 판정은 정상이다.
- 어느 하나의 기초자산이라도 현재가가 없으면 `W`는 산출 불가(`null`)이며, 조건 판정 결과도 `null`로 처리한다. 임의의 기본값을 대입해서는 안 된다.
- **기초자산이 0건이면 산출 불가가 아니라 전제조건 위반이다.** `null`을 반환하지 않고 **거부한다.**

> **0건과 E-01의 `null`은 성질이 다르다.** E-01의 `null`은 시세가 수집되면 값이 생기는 **일시적** 상태다. 기초자산 0건은 DOC-002 I-07이 금지한 **구조적** 위반이며 시세를 기다려도 해소되지 않는다. 둘을 같은 `null`로 반환하면 화면이 "시세 없음"을 표시하면서 영원히 오지 않을 시세를 기다리게 된다. §9.1이 E-01의 `null`(판정 보류)과 E-05의 `null`(판정 대상 아님)을 구분한 것과 같은 이유다.
>
> 거부는 §9의 예외 처리 대상이 아니다 — E-표는 **발생할 수 있는 상황**의 처리 규칙이고, 0건은 발생해서는 안 되는 입력이다. `tax_brackets`가 빈 목록으로 주입되는 경우를 시드 오류로 보고 거부하는 것(§5.1)과 같은 부류다.

### 3.2 조기상환 조건

n차 평가일에 대하여:

```
조기상환 충족  ⟺  W ≥ B(n)
```

### 3.3 리자드 조건

n차에 리자드가 정의된 경우(`lizard_barrier IS NOT NULL`)에만 평가하며, **조기상환 조건이 충족되지 않았을 때에만** 판정한다.

```
리자드 충족  ⟺  W < B(n)
              ∧  W ≥ L(n)
              ∧  ( lizard_requires_no_ki = false  ∨  KI 미터치 )
```

판정 우선순위는 다음과 같다.

```
1. W ≥ B(n)          → 조기상환 (EARLY)
2. 리자드 충족        → 리자드상환 (LIZARD)
3. 그 외              → 다음 차수로 이월
```

### 3.4 KI 상태

```
KI 미설정   ⟺  ki_barrier IS NULL          (노낙인 상품)
KI 터치됨   ⟺  ki_touched_at IS NOT NULL
KI 미터치   ⟺  위 두 경우가 아님
```

**보조 판정.** 수집된 시세로 `W < ki_barrier`가 관측되면 터치 후보로 표시하고 사용자 확인을 요청한다. 시스템이 자동으로 `ki_touched_at`을 확정하지 않는다(DOC-002 D-04). 관측 방식(`ki_observation`)이 `CONTINUOUS`인지 `CLOSING`인지에 따라 요구되는 데이터가 다르므로, `ki_barrier`가 있으면 관측 방식도 반드시 있어야 한다(DOC-002 I-11).

> **`ki_barrier IS NULL`이면 `ki_touched_at`을 보지 않는다.** 위 표의 첫 줄부터 `ki_barrier`가 있는 상품을 전제하며, E-06이 노낙인 상품의 KI 판정을 생략하고 리자드의 KI 요구 조건을 항상 충족으로 처리한다. 따라서 `ki_barrier`가 없는데 `ki_touched_at`이 기록된 행은 **그 기록이 판정에서 완전히 무시되고**, 리자드 상환이 잘못 판정되어 수령액이 어긋난다. 이 명세는 그런 행의 존재를 전제하지 않으므로 DOC-002 I-15가 저장 시점에 막는다 — 판정 알고리즘을 바꾸는 것이 아니라 입력의 정의역을 좁히는 것이다.

**표시 등급 (참고)**

| 조건 | 상태 | 코드 값 |
|---|---|---|
| `ki_touched_at IS NOT NULL` | KI 터치 | `TOUCHED` |
| `W ≤ ki_barrier` | KI 이하 (확인 필요) | `BELOW` |
| `W ≤ ki_barrier × 1.1` | 주의 | `WARNING` |
| 그 외 | 안전 | `SAFE` |

> **위 「상태」 열은 조건과 등급의 대응을 보이기 위한 참고 표기이고, 화면에 나가는
> 문자열의 정본은 DOC-005 §6.1이다 (v0.6).** 그 표는 `BELOW`를 「KI 배리어 하회」로
> 적는다 — DOC-005 §9가 「KI 배리어」를 표준 표기로 정했고 「확인 필요」는 등급이
> 아니라 **조치**를 말하는 표현이어서 조치 목록(`attentionReason.KI_BELOW`)에만
> 붙기 때문이다. 노낙인 상품은 이 표의 정의역 밖이며 코드 값이 `NO_KI`다.

## 4. 수령액 및 과세 금융소득

### 4.1 예상 수령액 (미상환 상품)

n차에 상환된다고 가정할 때의 세전 수령액.

```
grossExpected(n) = P × ( 1 + r × (m × n) / 12 )
```

`P`와 결과는 **상품 통화**다 *(v1.4)*. 식은 통화와 무관하므로 달러 상품도 같은 식을 쓰고 결과가 달러다 — 원화로 바꾸는 것은 과세 축에서만이며 §4.8이 한다.

**적용 쿠폰율.** 위 식의 `r`은 상수가 아니라 판정 결과(§3.3)에 따라 선택된 값이다.

```
applicableCouponRate(condition, r, lizardCouponRate)
  = r                     if condition = EARLY
  = lizardCouponRate      if condition = LIZARD
```

- `CARRY_OVER`는 해당 차수에 상환되지 않으므로 적용 쿠폰율이 정의되지 않는다. 호출 대상이 아니다.
- 아직 평가일이 도래하지 않은 차수는 판정값이 없으므로 **`EARLY`(정상 조기상환)를 가정한다.** 예상 수령액은 추정값이며, 리자드 상환을 가정하려면 호출부가 `LIZARD`를 명시한다.
- `condition = LIZARD`이고 해당 차수의 `lizard_coupon_rate`가 `NULL`이면 **오류로 처리한다.** 원금만 상환되는 리자드 변형은 `0`으로 표기하며 `NULL`로 표기하지 않는다(Q-04). `NULL`을 `0`이나 `r`로 임의 대체하면 수령액이 실제와 어긋난다 — 전자는 과소, 후자는 과대 추정이다.

### 4.2 확정 수령액 (상환 완료 상품)

`redemptions.gross_amount`를 그대로 사용한다. 시스템 추정값으로 대체하지 않는다(DOC-002 A-04). **상품 통화다** *(v1.4)*.

### 4.3 과세 금융소득

```
if account_type = TAX_FREE:
    taxableIncome = 0                      # 비과세 계좌는 종합과세 대상 제외

elif 상환 완료:
    taxableIncome = redemptions.taxable_income      # 증권사 확정값

else:  # 미상환 (추정)
    taxableIncome = max(0, grossExpected(n) − P)
```

> **달러 상품 (v1.4).** 둘째 분기(확정값)는 거래내역의 **원화** 값이므로 그대로 과세 축이다 —
> 환산하지 않는다. 셋째 분기(추정)의 값은 **달러 이익**이며 과세 금융소득이 아니다. 과세 금융소득(원화)으로
> 바꾸는 것은 §4.8이고, 차수별 참고 원천징수(§4.5)는 이 달러 이익을 원화로 바꾸지 않은 채 쓴다.
> 원화 상품은 이 블록 그대로다 — 추정 환율을 지나지 않는다.

### 4.4 손실 상환의 취급

**ELS 손실은 다른 금융소득과 통산되지 않는다.** 따라서 손실 상환(`MATURITY_LOSS`)의 과세 금융소득은 음수가 아니라 `0`이다.

```
포트폴리오 손익  =  gross_amount − P        (음수 가능)
과세 금융소득    =  0                        (음수 불가)
```

예: A 상품에서 1,000만원 손실, B 상품에서 2,000만원 이익이 발생한 경우

| 항목 | 값 |
|---|---|
| 포트폴리오 순손익 | +1,000만원 |
| 과세 금융소득 | **2,000만원** (1,000만원이 아님) |

이 분기는 사용자가 오해하기 쉬우므로 UI에서 두 값을 별도 항목으로 표시한다.

**달러 상품은 두 값의 통화도 다르다** *(v1.4)* — 포트폴리오 손익은 달러, 과세 금융소득은 원화다. 그래서 원화로 보면 손해인데 과세 금융소득이 양수인 경우가 있다(§4.8 검산 A-5 — 원금 환차손익을 과세표준 밖으로 읽는 추론 위에서, RD-13). 용어 쪽 정리는 DOC-005 §8.5.

### 4.5 예상 원천징수와 세후 예상 수령액 (참고용 · 분리과세 기준)

미상환 차수의 **참고용** 세후 금액이다. 그 차수에 분리과세로 종결된다고 가정하며 비교과세(§5.2)를 반영하지 않는다.

```
expectedWithholding(n) = truncate( taxableIncome(n) × k.separateTaxationRate )
expectedNet(n)         = grossExpected(n) − expectedWithholding(n)
expectedPnl(n)         = grossExpected(n) − P                        (음수 가능)
```

- `taxableIncome(n)`은 §4.3의 **미상환 분기**다 — `max(0, grossExpected(n) − P)`. 상환 완료 상품의 확정값(`redemptions.taxable_income`)을 쓰지 않는다. 이 축 전체가 「예상」이므로 확정값을 섞으면 한 열에 추정과 확정이 공존한다.
- 비율은 §2의 주입 상수 `separateTaxationRate`다. **`separateTaxationIncomeTaxRate`(14%)가 아니다** — 원천징수액은 지방소득세를 포함한 실제 징수액이며 그 구분은 §2 각주가 정본이다. 잘못 고르면 10% 과소 징수가 그럴싸한 숫자로 지나간다.
- 절사 단위는 §2의 반올림 규칙(세액 최종값 = 원 단위 절사)을 따르고 RD-01에 따라 **주입받는다.**

**비과세 계좌는 원천징수가 없다.**

```
if account_type = TAX_FREE:
    expectedWithholding(n) = 0
    expectedNet(n)         = grossExpected(n)
```

§4.3이 비과세 계좌의 과세 금융소득을 `0`으로 정하므로 위 곱셈이 자동으로 0이 되지만 **분기를 명시한다.** 「곱해서 0」과 「부과 대상이 아님」은 화면이 다르게 말해야 하는 상태이고, 계약도 `accountType`을 함께 실어 그 구분을 나른다(DOC-011 §4.4).

**이 값은 §7.4의 세후 회수와 «다른 값»이다.** 한 표에 나란히 두면 안 된다.

| | `expectedNet` (본 절) | `netProceeds` (§7.4) |
|---|---|---|
| 단위 | **차수** (한 상품의 한 차수) | **(소유자, 귀속연도)** |
| 세율 | 분리과세율 하나 (`k.separateTaxationRate`) | 비교과세 최종 부담률 (§5.2·§5.4) |
| 입력 | 그 상품의 계약 조건뿐 | 그 해 전체 금융소득 `F`와 다른 종합소득 `A` |
| 성질 | **참고값.** 종합과세 대상이면 실제 부담은 이보다 크다 | 그 해의 추정 결론 |

**그러므로 「세후 회수」라고 부르지 않는다** — DOC-005 §4가 그 이름을 연도 단위 값에 이미 배정했다(절대 규칙 #9). 표준 용어는 **「세후 예상 수령액」**이며, 한 소유자의 한 해 `expectedNet`을 전부 더해도 `netProceeds`가 되지 않는다(DOC-005 §8.9).

**표시 정합성 — 세 값이 한 반올림값에서 파생된다.** `grossExpected(n)`을 원 단위로(달러 상품은 0.01달러로 — v1.4) 한 번 반올림한 뒤 그 값에서 나머지를 유도한다. 각각 따로 반올림하면 화면에서 `expectedNet + expectedWithholding ≠ grossExpected`가 되고 **사용자가 뺄셈으로 그것을 본다.** §5.3이 총세액을 1차 값으로 두고 지방소득세를 잔차로 구하는 것과 같은 판단이다.

그 대신 **DOC-011 §4.6의 과세 집계는 반올림하지 않은 값을 계속 쓴다.** `P × r × (m·n)/12`가 소수인 경우(`m·n/12`는 3이 `m·n`을 나누지 않을 때 유한소수가 아니다 — 예: `m ∈ {1,2,4,5}`에서 `n`이 3의 배수가 아닐 때. *v1.4 정정 — 종전 「`m ∈ {1,2,5}`에서」는 `m = 4`를 빠뜨렸고 `n`에 따라 유한인 경우를 가리지 않았다*) 두 경로가 **≤1원** 어긋날 수 있는데, 집계 쪽을 반올림하면 종합과세 기준금액 20,000,000의 경계가 움직인다. 행 하나의 자기 정합성이 여기서 이기는 이유는 **사용자가 화면에서 그 뺄셈을 할 수 있고 DOC-011 §4.6의 중간값은 볼 수 없다**는 것이다. *(v1.4 — 두 인용에 문서 접두사를 붙였다. 이 문서의 §4.6이 아니다.)*

**`EARLY` 가정의 한계.** `grossExpected(n)`이 §4.1의 `EARLY` 가정 위에 있으므로, 리자드 조건이 붙은 차수가 실제로 `LIZARD`로 상환되면 금액이 **이보다 작다**(`lizard_coupon_rate`가 적용된다). 화면은 그 차수에 리자드 표식을 함께 낸다.

**검산 — 검증 케이스가 «아니다».**

§10의 TC-01~22는 종합과세·건강보험료·조건 판정의 집합이며 이 산식은 그 집합에 넣지 않는다. 「TC-01~22」가 CLAUDE.md 절대 규칙 #1과 저장소 여러 곳에 문자열로 박혀 있어 스물셋째를 더하면 그 인용이 전부 낡는데, 이 산식의 검증은 `tests/tax/withholding.test.ts`가 어차피 한다.

| 입력 | `P = 50,000,000` · `r = 0.1722` · `m = 6` · `n = 1` · `GENERAL` · `k.separateTaxationRate = 0.154` |
| 예상 수령액 | 54,305,000 |
| 과세 금융소득 | 4,305,000 |

#### 달러 상품 — 달러 기준 참고 *(v1.4, 민서 결정 U8 · 구현 컷 a2)*

달러 상품의 차수별 참고 원천징수는 **달러로** 낸다. 추정 환율을 쓰지 않는다.

```
usdGain(n)             = max(0, grossExpected(n) − P)                     # 달러 이익 — §4.3 셋째 분기
expectedWithholding(n) = separateTaxationWithholding( usdGain(n), k,
                                                      rounding = { unit: 0.01, mode: TRUNCATE } )
expectedNet(n)         = grossExpected(n) − expectedWithholding(n)        # 같은 통화 안의 뺄셈
expectedPnl(n)         = grossExpected(n) − P                             # 달러
```

- 비율은 원화 상품과 같은 `k.separateTaxationRate`를 **조회한다** — 15.4%를 적지 않는다(절대 규칙 #5). 달라지는 것은 절사 단위뿐이고 그 값은 상품 통화의 보조단위다. 원화 상품의 단위는 `1`(§2 · RD-01) 그대로다.
- **입력은 과세 금융소득이 아니다.** 과세 금융소득은 원화이고(§2) 여기서 곱하는 것은 달러 이익이다. 그래서 이 값은 **`F`·SCR-401·SCR-402에 들어가지 않는다** — 그쪽은 늘 원화 과세표준이다(확정 = 거래내역, 추정 = §4.8). 「한 해의 `expectedNet`을 전부 더해도 `netProceeds`가 되지 않는다」는 위 규칙이 통화가 달라지면서 더 강해질 뿐이다.
- **세후 = 세전 − 참고 원천징수가 통화 안에서 성립한다.** 세 값이 모두 달러이고 위의 「한 반올림값」 규칙이 0.01달러로 그대로 적용된다. 원천징수만 원화로 두면 세 값 중 둘은 달러, 하나는 원이 되어 사용자가 그 뺄셈을 할 수 없다.
- **환율이 필요 없으므로 환율 저장이 이 값을 무효화하지 않는다** — 차수별 참고값을 보이는 자리(DOC-011 §4.4)가 환율과 무관하게 남는다(DOC-010 AQ-76). 환율이 없어도(E-09) 이 값은 정상이다.
- 비과세 계좌 분기는 위와 같다 — 0.00달러, 세후 = 세전.

**표시는 「≈」가 붙은 참고값이다 — 형식은 실재하고 금액은 근사다.** 근거는 EM2048 투자설명서 원문이다(`BEM2048.pdf`, 2026-09-30 확인 — DOC-005 「예상 원천징수」).

| 원문 | 이 값에 주는 뜻 |
|---|---|
| 「외화수익금에 대해 원천징수되는 세금은 원화로 징수 … 세금은 전액 외화수익금에서 자동으로 환전되어 원천징수」 · 「세후 이자배당소득 및 원금은 모두 미국달러(USD)로 지급」 | **「세후 달러」가 이 상품에 실재한다** — 원화 세액이 달러 수령액에서 환전되어 빠진다. 그래서 세후를 달러로 보이는 형식이 맞다 |
| 과세표준은 「지급일의 … 매매기준환율 또는 재정환율에 의하여 환산한 금액」 | 실제 세액은 **원화로** 계산된다 — 달러 이익 × 지급일 환율에 소득세 14%와 지방소득세(소득세의 10%)를 각각 10원 미만 절사한다(RD-01 보강의 읽기). 15.4%를 한 번 곱하는 산식은 그보다 원화로 **0~19원 크고**, 달러 참고값은 여기에 센트 절사가 반대쪽으로 더해져 실제 달러 차감액과 **−1센트~+1.5센트** 안에서 갈린다(환전 환율 = 지급일 환율일 때 — 아래 각주) |
| 환전 차감에 쓰는 환율 — 원문에 없다 | **미확인.** 원화 세액을 달러로 되돌리는 환율에 따라 수 센트 어긋날 수 있다 |

발행사마다 징수 방식이 다르다(미래에셋은 원화예수금, 키움·NH·교보는 달러에서 차감 — RD-13 ⓒ). 그래서 화면은 이 값 옆에 「참고 — 실제 세액은 지급일 환율로 원화 계산 후 달러에서 환전 차감되며 발행사에 따라 방식이 다르다」는 취지를 붙인다(문구의 정본은 DOC-008).

> **두 범위는 실측이다 (2026-09-30, 저장소의 `truncateToUnit`).** ① 원화 과세표준 `X`가 원 단위
> 정수일 때 현 산식 `trunc₁(X × 0.154)`와 두 단계 절사 `trunc₁₀(X × 0.14) + trunc₁₀(trunc₁₀(X × 0.14) × 0.1)`의
> 차를 `X` = 1~200,000 전수로 쟀다 — 최소 0, 최대 **19**원(`X` = 708). 차이의 주기가 5,000원이므로
> (`0.14 × 5,000 = 700`이 100의 배수이고 `0.154 × 5,000 = 770`이 정수다) 그 구간이 전 구간과 같다.
> 지방소득세를 1원 절사로 읽으면 최대 **10**원이다. **19원은 닿는 상한이다** — 소득세 `A = trunc₁₀(X × 0.14)`가
> 10의 배수라 `1.1 × A`가 정수이므로 차는 `trunc₁(1.1 × r₁) + r₂`로 갈린다(`r₁` = 소득세 절사 잔여,
> `r₂` = 지방소득세 절사 잔여). `X`가 정수면 `X × 0.14`는 소수 2자리라 `r₁ ≤ 9.98`이고 `r₂`는 정수 0~9다
> (`A × 0.1`이 정수). 그래서 차 ≤ `trunc₁(1.1 × 9.98) + 9` = 19 < 20이고 `X` = 708(`r₁` = 9.12 · `r₂` = 9)에서
> 닿는다. 지방소득세 1원 절사의 10은 `r₂ = 0`인 경우 — `trunc₁(1.1 × 9.98)` = 10이다. ② 달러 참고값 `trunc₀.₀₁(g × 0.154) × x₁`과 실제
> (`X = trunc₁(g × x₁)`의 두 단계 절사)의 차를 달러 이익 `g` = $0.01~$2,000.00 전수 × `x₁` 넷
> (1,300 · 1,385.2 · 1,450 · 1,500)으로 쟀다 — 원화로 **−14~+19.82원**, 달러로 **−0.0098~+0.0146달러**다.
> 환전 차감 환율이 지급일 환율과 다르면 그 차이가 더해지며 그 값은 원문에 없다.

**검산** — §4.8 검산 A-1의 차수: 세전 **$10,600.00** · 원천징수 ≈ **$92.40** · 세후 ≈ **$10,507.60** · 예상 손익 +$600.00. 원화로 대조하면 870,000원 × 15.4% = 133,980원이고 두 단계 10원 절사로도 121,800 + 12,180 = 133,980원이라 이 입력에서는 차이가 0이다($92.40 × 1,450 = 133,980원). 저장소의 `separateTaxationWithholding`에 2026 상수와 `rounding.unit = '0.01'`을 넣어 실측했다.

**§10의 TC-01~22와 §3의 판정 규칙은 무변경이다**(절대 규칙 #1). 원화 상품의 위 검산 블록도 무변경이다.

> **§4.6은 비워 둔다 (v1.4).** v1.3까지 이 문서의 본문이 접두사 없이 쓴 「§4.6」 넷(§4.5 둘 ·
> §7.2 각주 · RD-02)은 전부 **DOC-011 §4.6**(`getTaxSummary`)이었고 v1.4에서 접두사를 붙였다.
> 그래도 이 번호를 쓰지 않는다 — 변경 이력 v1.0 행(기록이라 고치지 않는다)과 커밋 메시지에 남은
> 옛 인용이 새 절을 가리키게 되기 때문이다. **§4.7은 월수익 금액의 자리다(컷 b1).**

### 4.8 원화 환산 — 달러 상품의 추정 과세 금융소득 *(v1.4 신설 · 추정 전용 · 구현 컷 a2·a3)*

달러 상품의 과세 금융소득은 원화다(§2). **확정값은 거래내역의 원화 값을 그대로 쓰고 환산하지 않는다**(§4.3 둘째 분기, DOC-001 A-04). 이 절은 **아직 오지 않은 지급의 추정**만 원화로 바꾼다 — 원화 환산은 추정 전용이다(DOC-005 「원화 환산」).

```
x(c, asOf) = e.rate   where e ∈ exchange_rates, e.currency = c,
                            e.as_of_date = max{ as_of_date ≤ asOf }
           = 없음      if 그런 행이 없다

taxableIncomeKrw(els) =                       # 달러 상품, 기준일 asOf
    0                                   if account_type = TAX_FREE       # x 없이도 0 — 검산 A-2
    redemptions.taxable_income          if 상환 완료                       # 원화 확정값. 환산하지 않는다
    0                                   if grossExpected(n) − P ≤ 0       # 곱할 달러 이익이 없다
    ( grossExpected(n) − P ) × x        if x 있음                          # 달러로 빼고 한 번 곱한다
    null                                otherwise                         # E-09 (§9.3)
```

원화 상품은 §4.3 그대로다 — **`x = 1`을 곱하는 것이 아니라 이 경로를 지나지 않는다.** 원화 상품의 모든 값이 바이트 단위로 불변인 근거가 그것이다.

**`x`는 하나다 — RD-09 해결.** 기준일 이전(`as_of_date ≤ asOf`) 최신 1건을 **모든 건과 모든 미래 연도에** 쓴다. 연도별 전망 환율도, 지급일마다의 환율도 두지 않는다(DOC-001 A-07). 상한은 §3.1 「최신가」와 같은 이유로 둔다 — 미래 일자의 환율 행이 있어도 기준일의 추정에 섞이지 않는다. **기한으로 끊지 않는다** — 오래된 환율도 쓰고 기준일을 함께 나른다(`exchangeRateBasis`, §9.3). 화면이 「1,392.40원/달러 · 09-28 기준」처럼 그 날짜를 말하므로 오래됨은 표시의 몫이다(§3.1의 최신가도 기한이 없고, 오래됨은 판정이 아니라 표시 「시세 경과」(`isStale`, DOC-005)가 말한다). 기한으로 끊으면 E-09가 되어 과세 추정이 통째로 빠지는데, 그쪽이 오래된 환율보다 크게 틀린다.

**적용 환율은 `x`가 아니다.** 상환 기록의 `exchange_rate`는 거래내역에 적힌 참고값이며 계산에 쓰지 않는다(DOC-005 「적용 환율」) — 같은 상품의 추정에도, 아래의 수령액 환산에도 쓰지 않는다.

**기본 환율이 없다.** `1`·상수·과거 평균 모두 쓰지 않는다. `1`을 넣으면 검산 A-1의 870,000원이 **600원**이 되어(약 1/1,450) 그럴싸한 숫자로 지나간다 — 없으면 E-09로 가고 그 사실을 센다.

**TAX_FREE와 달러 이익 ≤ 0은 `x`보다 먼저다 — 이익 ≤ 0이면 환율 없이 0이다.** 둘 다 환율 없이 값을 **안다** — 0이다. 그래서 E-09로 세지 않는다(검산 A-2). 달러 이익 0은 원금상환형 리자드(Q-04 — `lizard_coupon_rate = 0`)처럼 `grossExpected(n) = P`인 차수다. 지금의 추정에서 음수 이익은 나오지 않지만(§4.1은 `r ≥ 0`) **분기는 `= 0`이 아니라 `≤ 0`이다** — 컷 b1의 월지급식 상품은 그 달 월수익을 상환에 합치지 않으므로 상환 금액이 원금 이하이고(RD-12) 그 상환 추정도 이 분기로 0이 되어야 한다. 이 분기를 빠뜨리면 월지급 달러 상품의 상환 추정이 전부 E-09로 세어져 「환율이 없어 빠졌다」는 거짓 경고가 뜬다(A-2의 틀린 답과 같은 부류).

**원화로 바꾼 두 금액의 차가 아니다.**

```
금지:  gross × x₁ − P × x₀          # x₁ = 지급일 환율, x₀ = 청약일 환율 (이 문단에서만 쓰는 기호)
```

달러로 이익을 먼저 구하고 **한 번** 환산한다. 근거는 투자설명서 문언이다 — 「발행가액 대비 초과소득」을 「지급일의 … 매매기준환율 또는 재정환율에 의하여 환산한 금액」으로 과세표준을 삼는다(EM2048 원문 · 미래에셋·NH·교보 투자설명서 · 국세청 예규 원천세과-222·법인46013-342가 같은 방향). 그래서 **원금의 환차익은 과세표준에 들어가지 않는 것으로 읽는다.** **이것은 추론이다** — 원금 환차익 비과세를 명시한 1차 출처는 미확인이다(RD-13 ⓐ). 틀린 산식은 두 방향으로 틀린다: 원화로는 손해인데 달러 이익이 있으면 과세를 **지우고**(검산 A-5), 달러 손실인데 원화로는 이익이면 원금 환차익을 **과세한다**(검산 A-6). 청약 환율 `x₀`은 저장하지 않으므로(DOC-002 DQ-15) 지금은 그 식을 계산할 수도 없지만, 청약 환율 열이 생기는 날(DQ-15 · RD-15) 이 금지가 그 열을 과세 축에 끌어들이지 못하게 한다.

**반올림.** `taxableIncomeKrw`는 **반올림하지 않은 채** `F`에 들어가고(§2 「집계는 반올림하지 않는다」) 표시만 1원 반올림한다. 곱하는 달러 이익은 **반올림하지 않은 값이다** — 0.01달러 반올림은 표시의 몫이고(§4.5 「표시 정합성」) `m ∈ {1,2,5}`처럼 `m·n/12`가 유한소수가 아닌 차수에서는 그 이익도 유한소수가 아닐 수 있다(§4.5 「그 대신」). 그래서 곱은 정확하지 않고 Decimal의 유효자릿수 40(`src/lib/decimal.ts`)에서 끊긴다 — 실측(2026-09-30, 저장소의 `grossExpected`)으로 `P` $10,000.00 · `r = 0.1` · `m = 1` · `n = 1` · `x = 1,392.4`의 곱 116,033.33…원이 유리수 정답과 **5 × 10⁻³³원** 안에서 같다. 원화 상품의 과세 집계가 이미 같은 조건으로 돈다. 실제 과세표준은 1원 미만을 버리므로(RD-01) 건당 1원 미만이 어긋나지만, `x` 자체가 가정이라 그 차이보다 `x`의 오차가 훨씬 크다.

**같은 `x`로 수령액과 원금도 바꾼다 — 전망 전용.** 원화 합계가 필요한 자리는 DOC-011 §4.7(`netProceeds`의 `Σ gross`, `remainingPrincipal`)과 SCR-101의 원화 환산 합계(§7.7)뿐이다.

```
grossKrw(els)     = gross × x          # gross = grossExpected(n) 또는 redemptions.gross_amount
principalKrw(els) = P × x
```

같은 `x`이므로 한 상품이 잔여 원금(`P × x`)에서 세후 회수(`gross × x − 세액`)로 옮겨 갈 때 차이는 **달러 이익 × x뿐이다** — 전망에 환차손익이 생기지 않는다(RD-15). 확정 상환의 실수령액도 `x`로 바꾸므로(적용 환율을 쓰지 않는다) 그 **원화 값은 추정이다** — 확정인 것은 그 상환의 원화 과세 금융소득뿐이다(§7.5).

**월수익 건**(`c(k) × x`)의 환산은 컷 b1이 이 절에 더한다(§4.7).

**단계.** 컷 a2(배포 웨이브 W1)에는 `exchange_rates`가 없다 — **일반계좌 달러 상품의 추정은 전부 E-09다.** 그것이 W1의 설계된 상태이며 결함이 아니다(확정 원화 과세는 그때도 들어간다). 컷 a3(W2)이 `exchange_rates`와 수동 입력(DOC-011 §5.13)을 세우면서 `x`가 생긴다.

### 5.1 누진 산출세액 함수

```
T(x) = 0                                          if x ≤ 0
     = x × rate(x) − progressiveDeduction(x)      otherwise
```

### 5.2 비교과세

금융소득이 종합과세 기준금액을 초과하는 경우, 두 방식으로 산출한 세액 중 **큰 값**을 적용한다. 이하 `k`는 2장의 주입 상수 집합을 가리킨다.

```
방식 ①(분리 기준) = F × k.separateTaxationIncomeTaxRate + T(A)
방식 ②(종합 기준) = k.comprehensiveTaxationThreshold × k.separateTaxationIncomeTaxRate
                  + T( max(0, F − k.comprehensiveTaxationThreshold) + A )

산출세액 = max( 방식①, 방식② )
```

두 방식은 **소득세만** 산출한다. 지방소득세는 5.3에서 가산하므로 여기서 15.4%가 아니라 소득세분 14%를 쓴다(2장 참조).

**금융소득 귀속세액**(국세)은 전체 산출세액에서 금융소득이 없었을 때의 세액을 차감하여 구한다.

```
def financialIncomeTax(F, A, k):
    if F ≤ 0:
        return 0
    if F ≤ k.comprehensiveTaxationThreshold:
        return F × k.separateTaxationIncomeTaxRate      # 분리과세로 종결

    method1 = F × k.separateTaxationIncomeTaxRate + T(A)
    method2 = k.comprehensiveTaxationThreshold × k.separateTaxationIncomeTaxRate
            + T( max(0, F − k.comprehensiveTaxationThreshold) + A )
    return max(method1, method2) − T(A)
```

**기준금액 이하의 조기 반환은 생략할 수 없다.** 비교과세식을 기준금액 이하 구간까지 확장하면 틀린 값이 나온다. `F = 10,000,000`, `A = 0`인 경우 방식① = 1,400,000, 방식② = 2,800,000이므로 `max(①,②) − T(A) = 2,800,000`이 되지만, 정답은 원천징수로 종결되는 1,400,000이다. 방식②는 기준금액까지를 항상 전액 과세한 것으로 계산하므로 기준금액 미달 구간에서 성립하지 않는다. 두 방식이 교차하는 구간은 `F > k.comprehensiveTaxationThreshold`뿐이다.

**방식①·방식②의 표시.** `F ≤ k.comprehensiveTaxationThreshold`인 경우 비교과세를 적용하지 않으므로 두 방식 값은 의미가 없다. 화면·계약 계층에는 값이 아니라 **미적용(null)** 으로 전달한다(DOC-011 §4.6).

**`A`의 취급.** `A`가 미입력(null)인 경우와 `0`인 경우의 결과는 동일해야 한다. 구현 시 `A = coalesce(A, 0)`으로 정규화한다.

### 5.3 지방소득세

지방소득세는 소득세액에 `localIncomeTaxRate`(2026년 10%)를 곱한 값이다.

```
localIncomeTax(F, A) = financialIncomeTax(F, A) × k.localIncomeTaxRate
totalTax(F, A)       = financialIncomeTax(F, A) × ( 1 + k.localIncomeTaxRate )
```

### 5.4 최종 부담률

```
effectiveRate(F, A) = totalTax(F, A) / F        (F > 0)
                    = 0                          (F ≤ 0)
```

### 5.5 추가납부 예상액

상환 시점에 원천징수가 이미 이루어졌으므로, 종합과세 확정 세액과의 차액만 추가 납부한다. 원천징수액은 지방소득세를 포함한 실제 징수액이므로 `separateTaxationRate`(2026년 15.4%)를 쓴다.

```
withheld(F)         = F × k.separateTaxationRate
additionalTax(F, A) = max( 0, totalTax(F, A) − withheld(F) )
```

**중요 — 추가납부 0이 정상인 경우.** `A`가 작을 때 방식①이 방식②보다 크면 실효세율이 원천징수율로 유지되어 추가납부가 발생하지 않는다. 이는 오류가 아니다.

다른 종합소득이 없는 경우(`A = 0`) 추가납부가 처음 발생하는 지점은 **F = 77,600,000원**이다. 2026년 상수로 유도하면 다음과 같다.

```
방식① = 방식②
F × 0.14 = 20,000,000 × 0.14 + (F − 20,000,000) × 0.24 − 5,760,000
0.14F − 2,800,000 = 0.24F − 10,560,000
0.10F = 7,760,000
F = 77,600,000
```

이 임계값은 `A`에 따라 이동하므로 하드코딩하지 않는다. 위 값은 검증 케이스(10장)의 기준점으로만 사용한다.

### 5.6 구간별 실질 한계 부담률

## 6. 건강보험료

### 6.1 가입유형별 산정 소득

```
def insuranceBase(F, type, k):
    if type = REGIONAL:      # 지역가입자
        return F if F > k.regionalIncomeThreshold else 0    # 초과 시 전액 반영
    if type = EMPLOYEE:      # 직장가입자
        return max(0, F − k.employeeNonWageThreshold)       # 보수외소득 초과분만
    if type = DEPENDENT:     # 피부양자
        return F if F > k.dependentIncomeThreshold else 0   # 초과 시 자격 상실 → 전액
    return 0                                                # NONE
```

문턱 구조가 유형별로 다르다는 점에 유의한다. 지역가입자는 `regionalIncomeThreshold`(2026년 1,000만원) 초과 시 **전액**이 반영되므로 문턱 부근에서 부담이 계단식으로 증가한다.

세 문턱은 2026년 기준으로 각각 1,000만·2,000만·2,000만원이나 **서로 다른 상수**다. 뒤의 두 값이 종합과세 기준금액과 같은 것도 우연이며, 근거 법령이 다르므로 하나의 상수로 공유하지 않는다(2장 참조).

### 6.2 보험료 산출

```
healthInsurance(F, type) = insuranceBase(F, type, k) × k.healthInsuranceRate
longTermCare(F, type)    = healthInsurance(F, type) × k.longTermCareRate
totalInsurance           = healthInsurance + longTermCare
```

장기요양보험료는 금융소득이 아니라 **건강보험료에** 비율을 곱한 값이다(DOC-005 §5).

### 6.3 산출값의 한계

지역가입자 보험료는 실제로는 주민등록세대 단위로 소득·재산을 합산하여 부과되나, 본 시스템은 세대 구성과 재산을 모델링하지 않는다. 따라서 산출값은 **개인의 금융소득만 반영한 추정치**이며 실제 부과액과 차이가 있다(DOC-001 A-06). 이 취지를 UI에 고지한다.

## 7. 연도별 집계

### 7.1 집계 단위

집계 키는 항상 **(소유자, 귀속연도)** 다. 사용자 간 합산은 어떤 경우에도 수행하지 않는다(DOC-002 D-02).

집계는 **평탄한 합산이 아니라 키별 분할**로 정의한다. 여러 소유자·연도가 섞인 항목 집합을 받으면 키별로 나누어 각각 집계하며, 서로 다른 키의 값이 하나의 합계에 들어가는 경로를 두지 않는다.

```
groupByOwnerYear(items) = [ (key, { item ∈ items | key(item) = key }) | key ∈ distinct(key(items)) ]
```

단일 키 집계는 키를 **명시적 인자로 받고**, 키와 다른 항목이 섞여 있으면 거부한다.

```
aggregateFinancialIncome(key, items) = ERROR         if ∃ item ∈ items : key(item) ≠ key
                                     = (key, F)      otherwise
```

집계 결과는 항상 키를 동반한다. 값만 반환하면 이후 단계에서 어느 소유자·연도의 값인지 알 수 없고, 두 사람의 결과를 같은 변수에 담는 실수가 드러나지 않는다.

> **왜 키를 인자로 받는가.** 항목 배열만 받고 "호출부가 이미 필터링했다"고 가정하면 규칙은 주석으로만 존재한다. 키를 명시하면 위반이 함수 경계에서 드러난다. 키가 컴파일 시점에 알려진 경우(리터럴·상수)에는 타입 수준에서 거부되고, 런타임 UUID인 경우에는 같은 규칙을 실행 시점에 검사한다. 두 방어는 대체 관계가 아니라 보완 관계다.

### 7.2 귀속연도 결정

```
상환 완료: year( redemptions.redemption_date )
미상환   : year( 적용 차수의 evaluation_date )
```

미상환 상품의 적용 차수는 **다음 도래 평가일의 차수**로 가정한다. 세 경우에는 정할 수 없다 — 전 차수 경과 미상환(§9.2) · 평가일정 0건 · 만기 상환인데 일정 0건(이 경우는 상환일 기준이 먼저 적용된다). §7.5가 그 셋을 특수 처리 없이 흡수한다.

> **사용자 지정은 기본값을 바꾸지 않는다 (RD-02 해결, P4b).** 「다음 도래 평가일」을 **기본값으로 확정 유지**하고, 사용자 조정은 DOC-011 §4.7 `getForecast` 전용의 **비영속 `scenario` 인자**로 둔다(저장하지 않는다). 근거 셋 — ① 기본값을 바꾸면 DOC-011 §4.1·§4.3·§4.6·§4.8이 전부 값이 달라지는데 그것들은 이미 실측·검증된 상태다 ② DOC-011 §4.6의 `override`(비영속 시뮬레이션)라는 **동형의 선례**가 있다 ③ 영속 컬럼은 DOC-002 DQ-05(유도값 저장 금지)·RD-06과 정면으로 어긋나고 DOC-010 AQ-29의 우회면을 넓힌다. **스키마 변경 0, 호출부 변경 0.**
>
> **`scenario`의 규칙은 본 절이 아직 정하지 않았다** — 선택 가능한 차수 범위, 경과한 차수를 지정했을 때, 없는 차수를 지정했을 때가 열려 있다. 구현이 P4c로 배정되었으므로 그 규칙도 그때 여기에 신설한다(DOC-008 §9 SQ-07). 기본값만으로도 §7.5가 완결되는 것이 분리의 근거다.

### 7.3 연도별 금융소득

```
F(owner, year) = Σ taxableIncome(els)                     # 해당 소유자·연도의 ELS
               + tax_profiles.other_financial_income      # ELS 외 금융소득
```

합산 대상은 §7.1의 키에 속한 항목뿐이다. `other_financial_income`도 `(owner, year)`에 귀속된 값이므로 다른 소유자·연도의 값을 더할 수 없다.

**`Σ`의 항은 건별 원화 과세 금융소득이다** *(v1.4)*. 위 식은 그대로이고 항이 무엇인지를 좁힌다.

```
F(owner, year) = Σ taxableIncomeKrw(e)     for e ∈ 그 키의 건, taxableIncomeKrw(e) ≠ null
               + tax_profiles.other_financial_income

taxableIncomeKrw(e) = §4.3의 값                          원화 상품 — 확정·추정 모두 (불변)
                    = redemptions.taxable_income          달러 상품의 확정 상환 — 거래내역의 원화 값
                    = §4.8의 값 (null 가능)                달러 상품의 추정
```

- 「건」은 지금 상품의 상환 한 건(확정 또는 추정)이다. **월수익 건은 컷 b1이 더한다**(DOC-002 D-09) — 식의 모양은 그대로이고 항이 늘 뿐이다.
- `null`인 건(E-09)은 **더하지 않고 센다**(§9.3). 0으로 바꿔 더하면 빠졌다는 사실이 사라진다.
- `aggregateFinancialIncome`의 키 검사(§7.1)는 **그대로다.** 들어가는 값이 원화라는 것은 이 함수가 아니라 상류가 보장한다 — 확정값은 원화 열에서 오고(DOC-002 M-08) 추정은 §4.8을 지난다. 달러 금액이 원화 자리에 들어오면 형식이 정상이고 값만 거짓이므로(검산 A-4의 15,004,000) 그 경계는 조회 사상(`contributionOf`, DOC-011 §4.6)에서 단언한다.

`A`는 `tax_profiles.other_income_base`에서 조회한다. `A` 역시 개인 단위이므로 `F`와 같은 소유자의 값이어야 한다.

### 7.4 세후 회수액

```
netProceeds(owner, year) = Σ gross(els) − F(owner, year) × effectiveRate(F, A)
```

비과세 계좌 상품은 `taxableIncome = 0`이므로 세액이 부과되지 않고 `gross`가 전액 반영된다.

건강보험료는 차감하지 않는다. 세액만 반영하는 것이 이 정의이며, 보험료는 §6이 별 산식으로 낸다.

**`gross`는 원화다** *(v1.4)*. 달러 상품의 `gross`는 §4.8의 같은 `x`로 바꾼 값이며 **추정**이다 — 확정 상환의 실수령액도 적용 환율이 아니라 `x`로 바꾼다. `x`가 없으면 그 상품의 `gross`는 이 합에서 빠지고 센다(§7.5 「달러 상품」 · §9.3).

### 7.5 다년도 누적과 잔여 원금

§7.1~§7.4는 **유량**(그 해에 회수한 것)을 정의한다. 본 절은 **저량**(그 시점에 남아 있는 것)과 유량의 누계를 정의한다. 둘 다 집계 키가 `(소유자, 귀속연도)`이므로 §7에 둔다 — 이 장의 조직 원리는 「유량」이 아니라 그 키다(§7.1이 첫 절인 이유).

```
redeemedBy(els, Y) = true   if 상환완료 ∧ year(redemption_date) ≤ Y
                   = true   if 미상환 ∧ 적용차수 존재 ∧ year(적용차수 evaluation_date) ≤ Y
                   = false  otherwise

remainingPrincipal(owner, Y) = Σ P(els)  for els ∈ owned(owner) where ¬redeemedBy(els, Y)
cumulativeNet(owner, Y)      = Σ netProceeds(owner, y)  for y ∈ [Y₀, Y]
cumulativeAssets(owner, Y)   = cumulativeNet(owner, Y) + remainingPrincipal(owner, Y)
```

`Y₀`는 전망의 시작 연도이며 기준일의 연도다. 적용 차수는 §7.2가 정한다.

#### 측정 시점은 귀속연도의 말이다. 기준일이 아니다

DOC-005 §8.8의 「특정 **연도 말**」은 표기 문제가 아니라 **이중 계상 스위치**다. 기준일에서 재면 `asOf` 이후 같은 해에 상환되는 상품이 유량과 저량 **양쪽에** 잡힌다.

**검산** — A(원금 1억, 쿠폰 1천만, 2026-11-15 상환 가정) · B(원금 1억, 쿠폰 3천만, 2029 상환 가정) · `asOf = 2026-07-28` · 둘 다 일반계좌, 소유자 하나, ELS 외 금융소득 0, `A = 0`.

| 값 | 2026 | 2029 |
|---|---|---|
| `F` | 10,000,000 | 30,000,000 |
| 종합과세 | 아니다 (기준금액 이하) | **그렇다** |
| 총세액 | 1,540,000 | 4,620,000 |
| 추가납부 | **0** | **0** |
| 최종 부담률 | 15.40% | 15.40% |
| `netProceeds` | 110,000,000 − 1,540,000 = **108,460,000** | 130,000,000 − 4,620,000 = **125,380,000** |
| `remainingPrincipal` | B의 100,000,000 | 0 |
| `cumulativeAssets` | **208,460,000** | **233,840,000** |

**연도 말 기준이 아니면 2026년이 308,460,000이 된다** — `asOf`(7월 28일)에는 A가 아직 미상환이므로 잔여 원금에 A의 1억이 남고, 그 해 유량에도 A의 회수가 들어간다. **정확히 A의 원금만큼 과대**하다.

`cumulativeAssets(2029)`를 다른 경로로 검산하면 같은 값이 나온다: 투입 200,000,000 + 쿠폰 40,000,000 − 세금 6,160,000 = **233,840,000** (6,160,000 = 1,540,000 + 4,620,000).

> **2029년의 추가납부가 0인 것이 정상이다.** `F = 30,000,000`은 기준금액을 넘어 비교과세로 가지만 방식①(4,200,000)이 방식②(3,400,000)보다 크고, 그 결과 총세액이 원천징수액과 같아진다. §5.5가 규정한 「추가납부 0이 정상인 경우」이며 분기점은 77,600,000이다(§10.1 TC-01·TC-02가 그 사이 구간을 고정한다).

#### 이중 계상이 없는 이유 — 엄격 부등호가 배타적·전체적 분할을 만든다

`gross(els)`가 **원금 반환분을 포함하므로**(§4.1) 한 상품은 `redeemedBy`의 참·거짓에 따라 두 항 중 **정확히 하나**에만 들어간다.

| `redeemedBy(els, Y)` | `cumulativeNet(Y)` | `remainingPrincipal(Y)` |
|---|---|---|
| 참, 귀속연도 ∈ `[Y₀, Y]` | 들어간다 (그 해 한 번) | — |
| 참, 귀속연도 `< Y₀` | — | — |
| 거짓 | — | 들어간다 |
| 적용 차수 없음 | — | 들어간다 (전 연도) |

**둘째 줄이 `cumulativeAssets`라는 이름의 근거다.** `Y₀` 이전에 상환된 상품은 어느 항에도 없다 — 그 연도의 세율 시드가 없으면 세후로 계산할 수 없고 계약이 그 연도를 거부하기 때문이다(DOC-011 §4.6). 즉 이 값은 「보유 자산의 총액」이 아니라 **전망 구간 안에서의 누적**이며, 「총자산」으로 부르면 거짓이 된다(DOC-005 §8.8).

#### 적용 차수가 없는 상품은 배제하지 않는다

§7.2가 적용 차수를 정할 수 없는 경우가 셋이다 — E-07(전 차수 경과 미상환, §9.2) · 평가일정 0건 · 만기 상환인데 일정 0건. 셋 다 **특수 처리 없이 흡수된다**: `redeemedBy`를 귀속연도가 아니라 **상환 레코드의 존재**로 정의했기 때문이다. 앞의 둘은 `false`가 되어 전 연도의 `remainingPrincipal`에 남고 `netProceeds`에는 기여하지 않는다. 셋째는 첫 가지(상환 완료)가 처리한다.

**배제하면 그 원금이 화면에서 조용히 증발한다.** 그 상품의 원금이 여섯 행 전부의 잔여 원금에 남아 「회수 시점을 모르는 자산」으로 보이는 것이 **정확한 표현이며 E-07의 시각적 형태다** — 화면은 그 사실을 말해야 한다(사용자에게는 결함처럼 보이므로). 없는 판단을 지어내지 않는 것과 값을 숨기지 않는 것이 같은 규칙이다.

#### 추정 표식은 두 축이다

| 축 | 참인 조건 | 어디에 |
|---|---|---|
| `hasEstimates` | 그 행의 값이 적용 차수 가정에 의존한다 — 그 해에 상환이 **가정된** 미상환 상품이 있거나, 연도 말에 남은 미상환 상품이 있다 | 행 단위 표식 |
| 화면 전체 고지 | 미상환 상품이 하나라도 있다 | 표 위 (DOC-008 §5) |

**둘을 하나로 두면 행 표식의 정보량이 0이 된다** — 미상환 상품이 하나라도 있으면 잔여 원금이 그 가정에 의존하므로 모든 행이 참이 되기 때문이다. 그래도 행 축의 정의를 좁히지 않는 이유는, 좁히면 「이 행의 잔여 원금은 추정인데 표식이 없다」가 되어 화면이 확정이라 말하면서 시점을 모르는 원금을 보여주게 된다는 것이다.

`hasEstimates`는 **그 행의 값에 원화 환산(§4.8)이 들어가도 참이다** *(v1.4)* — `x`가 가정이므로 확정 상환의 실수령액도 원화로는 추정이다.

#### 달러 상품 — 같은 `x`로 바꾸고, 환율이 없으면 그 상품의 원화 합만 뺀다 *(v1.4 · 구현 컷 a2(제외와 건수)·a3(환산))*

`redeemedBy`는 통화와 무관하다(상환 레코드의 존재와 적용 차수의 연도만 본다). 달라지는 것은 원화 합에 들어가는 **값**이다.

```
Σ gross(els)                 → 달러 상품은 gross × x               (§4.8)
remainingPrincipal(owner, Y) → 달러 상품은 P × x                   (§4.8)
F(owner, y)                  → §7.3 — 건별 원화 과세 (확정은 원화 그대로, 추정은 §4.8)
```

**배타적·전체적 분할이 원화에서도 성립한다** — 수령액과 원금을 **같은** `x`로 바꾸므로 위 「이중 계상이 없는 이유」의 표가 그대로이고, 한 상품이 두 항 사이를 옮겨 갈 때 생기는 차이는 달러 이익 × `x`뿐이다(환차손익이 생기지 않는다 — RD-15).

**`x`가 없으면 — 건 단위로 뺀다 (E-09, §9.3).**

| 값 | `x` 없음에서 | 이유 |
|---|---|---|
| 달러 상품 확정 상환의 원화 과세 금융소득 | **늘 `F`에 들어간다** | 거래내역의 원화 값이다 — 환율이 필요 없다(A-04) |
| 달러 상품 추정 건의 과세 금융소득 — 비과세 계좌이거나 달러 이익 ≤ 0 | **`0`** — `F`에 0으로 들어가고 세지 않는다 | 환율 없이 값을 안다(§4.8 · 검산 A-2) |
| 달러 상품 추정 건의 과세 금융소득 — 일반계좌 · 달러 이익 > 0 | `null` — `F`에서 빠지고 `unconvertedCount`로 센다 | 원화 값을 모른다 |
| 그 상품의 `gross`(해당 연도 — 뒤 행의 `cumulativeNet`·`cumulativeAssets`에도)와 `P`(잔여 원금) | **원화 합에서 빠지고 `excludedForeignCount`로 센다** — 행마다(§9.3) | 원화 값을 지어내지 않는다 |

**이것은 위 「배제하지 않는다」의 명시된 예외다.** 그 규칙은 「배제하면 원금이 조용히 증발한다」였고 그 판단의 뿌리는 「없는 판단을 지어내지 않는 것과 값을 숨기지 않는 것이 같은 규칙이다」였다. 여기서는 두 요구가 **갈린다** — 원화 원금을 보이려면 환율을 지어내야 한다. 그래서 짓지 않는 쪽을 택하고, 숨기지 않는 쪽은 **세기**로 지킨다: 빠진 상품 수(`excludedForeignCount`)를 전망이 보이고, 그 상품의 달러 원금은 사실 합계(§7.7)에 통화별로 남는다. **조용한 배제가 아니라 빠졌다는 사실을 보이는 배제다.**

- **상품 단위로 빼지 않는 이유**: 상품을 통째로 빼면 확정 원화 과세까지 `F`에서 사라진다. 그러면 전망 첫해의 `F(Y₀)`가 SCR-401의 `F`와 갈린다 — **두 경로는 같은 건을 빼야 한다**(같은 소유자·연도에서 `F(Y₀)` = DOC-011 §4.6의 `F`).
- **그 대가**: 확정 상환이 있는 해에 `x`가 없으면 그 해의 `netProceeds`가 그 상품의 세액(`F`에 들어갔다)은 빼고 수령액(빠졌다)은 더하지 않는다 — 원화 합이 그 상품의 세후 수령액만큼 작다. 건수 표시가 그 사실을 말한다.
- **세는 대상**: 전망 구간 `[Y₀, …]`에서 원화 값이 **필요한** 달러 상품만이다 — `Y₀` 이전에 상환된 상품은 어느 항에도 없으므로(「이중 계상이 없는 이유」 표 둘째 줄) 세지 않는다. **행마다 세고, 상환 연도에서 멈추지 않는다** — 상환 뒤의 행에서도 누적 두 열(`cumulativeNet`·`cumulativeAssets`)이 그 상품의 세후 회수를 잃으므로 마지막 행까지 1이다(§9.3 · DOC-011 §4.7).
- **단계**: 컷 a2에는 `exchange_rates`가 없으므로 전망 구간의 달러 상품이 **전부** `excludedForeignCount`에 든다. 컷 a3부터 `x`가 있으면 0이다.

> **§7.6은 월수익 건의 모델 자리다(컷 b1).**

### 7.7 사실 합계는 통화별이다 *(v1.4 신설 · 구현 컷 a2 — 원화 환산 합계는 a3)*

§7.1~§7.5는 원화의 집계다 — 과세 축과, 그 위에 선 전망의 원화 합. 본 절은 **사실**(투자원금·포트폴리오 손익)의 합계다 — 세금이 아니므로 `(owner, year)` 키가 아니라 한 소유자의 포트폴리오 단위이고, 달러 상품이 들어오면서 **통화**가 합의 키에 더해진다.

```
sumByCurrency(items)  = { c ↦ Σ amount(i) | i ∈ items, currency(i) = c }    # 통화를 넘어 더하지 않는다

투자원금(보유중)[c]    = Σ P(els)             for els 보유중,   currency(els) = c
포트폴리오 손익[c]      = Σ portfolioPnl(els)  for els 상환완료, currency(els) = c
portfolioPnl(els)      = gross_amount − P                                 # 받은 월수익의 합은 컷 b1이 더한다

원화 환산 합계 (추정)   = 투자원금(보유중)[KRW] + 투자원금(보유중)[USD] × x    # x가 없으면 «없다» (0이 아니다)
```

- **사실은 환산하지 않는다.** 환산하면 확정값이 추정이 된다 — 거래내역에서 옮긴 달러 금액이 오늘의 환율에 따라 움직이는 숫자가 되고, 화면의 「추정값과 확정값은 시각적으로 구분한다」(DOC-008 ST-05)가 합계 한 줄에서 무너진다.
- **원화 환산 합계는 투자원금(보유중)에만 둔다.** `x`와 그 기준일을 붙인 **추정**이며(「원화 환산 합계 약 …원 (추정 · 1,392.40원/달러 · 09-28 기준)」 — 문구의 정본은 DOC-008 SCR-101), `x`가 없으면 줄을 생략한다. **포트폴리오 손익은 원화로 바꾸지 않는다** — 달러 손익 × 오늘의 `x`는 원화 손익이 아니고(청약 환율이 필요하다 — DOC-002 DQ-15) 과세표준도 아니다. 이름이 없는 값이다(RD-15).
- **원화뿐인 포트폴리오는 지금과 같다** — 통화 줄이 하나이고 환산 줄이 없다. 바이트 단위 불변이 요구다.
- **`aggregateRealizedPnl`은 서명이 바뀌지 않는다** — TC-17이 그 함수를 직접 부른다(`tests/tax/aggregation.test.ts`). 전제만 명시한다: **한 통화의 항목만 받는다.** 호출부는 `sumByCurrency`로 먼저 가른다. `sumByCurrency`·`portfolioPnl`은 새 순수 함수다(`lib/domain`, 컷 a2). TC-17은 원화 한 통화라 영향이 없다.
- 절대 규칙 #7과 무관하다 — 사실 합계는 한 소유자의 상품만 보고(DOC-011 §4.1), 통화 키는 소유자 키 **안에서** 한 번 더 가르는 것이다.

## 8. 계산 파이프라인

화면 렌더링 시의 계산 순서. 하위 단계는 상위 단계의 결과에 의존한다.

```
1. 시세 조회        → asset_prices 최신값
2. 워스트오브 산출   → 상품별 W
3. 조건 판정        → 조기상환 / 리자드 / 이월, KI 상태   (보유중 상품만 — E-05)
4. 적용 차수 결정    → 사용자 지정 또는 다음 평가일        (경과 미상환 차수는 E-07)
5. 수령액 산출      → 확정값 또는 적용 쿠폰율 기반 추정값
6. 과세소득 산정     → 계좌유형·손실 규칙 적용
6a. 원화 환산       → 달러 상품의 추정만 × 추정 환율 x (§4.8). x가 없으면 그 건은 null (E-09)
7. 연도별 집계      → (소유자, 연도) 키별 분할 — 키를 넘어 합산하지 않는다. null 건은 더하지 않고 센다
8. 세액·보험료 계산  → 비교과세, 건강보험
9. 부담률·추가납부   → 표시값 산출
10. 다년도 누적·저량 → 연도 말 기준 잔여 원금, 누적 세후 회수·자산 (§7.5)
```

10단계는 SCR-402(다년도 전망)에서만 수행한다. 1~9를 전망 구간의 각 연도에 대해 반복한 뒤 그 결과를 누적하며, **측정 시점이 연도 말이라는 것**이 9단계까지와 다른 유일한 점이다(§7.5).

**6a단계** *(v1.4)* 는 과세 축만 바꾼다 — 1~3단계(판정)는 통화와 무관하고(§3.1) 5단계의 값은 상품 통화 그대로다. 10단계에서는 달러 상품의 수령액·원금도 같은 `x`로 바꾼다(§7.5 「달러 상품」). 사실 합계(§7.7)는 이 파이프라인 밖이다 — 통화별로 더하고 환산하지 않는다.

E-05와 E-07은 "무엇을 하지 않는다" 또는 "사용자에게 요청한다"로만 기술되어 있어 반환값이 정의되지 않았다. 두 항목의 계약을 아래에서 확정한다.

E-09는 v1.4에서 명세됐다 — 반환 계약은 §9.3이다(구현은 컷 a2·a3). E-10은 여전히 v1.3의 **등재**다 — 반환 계약은 컷 b1이 §9.4로 신설한다. 그 전까지 구현은 두 경우를 만들 수 없다(달러·월지급식 상품이 아직 저장되지 않는다 — 달러는 컷 a2부터).

### 9.1 E-05 반환 계약 — 상환 완료 상품

상태는 상환 레코드의 존재로 유도한다(DOC-002 §5.1). 조건 판정(§3.2·§3.3), KI 판정(§3.4), 시세 비교는 **보유중 상품에만 정의된다.**

```
asActive(params, redemption) = params     if redemption = NULL      # 보유중
                             = NULL       otherwise                 # 상환완료
```

판정 함수의 입력은 `asActive`의 반환값으로 한정한다. 상환 완료 상품에서는 `asActive`가 `NULL`을 반환하므로 판정 함수에 넘길 값이 애초에 존재하지 않는다.

| 대상 | 보유중 | 상환완료 |
|---|---|---|
| 조건 판정 (§3.2·§3.3) | `EARLY` / `LIZARD` / `CARRY_OVER`, 시세 없으면 `NULL` | **호출 불가** |
| KI 표시 등급 (§3.4) | `NO_KI` / `SAFE` / `WARNING` / `BELOW` / `TOUCHED`, 시세 없으면 `NULL` | **호출 불가** |
| KI 터치 후보 (§3.4 보조 판정) | `true` / `false` | **호출 불가** |

`asActive`가 `NULL`을 반환한 경우 호출부는 이를 **판정 생략**으로 표시한다. `CARRY_OVER`나 `SAFE` 같은 판정값으로 대체하지 않는다. 상환 완료 상품의 표시값은 판정 결과가 아니라 상환 실적(§4.2)이다.

> **`NULL`의 두 의미를 구분한다.** 판정 함수가 반환하는 `NULL`은 E-01(시세 없음 → 판정 보류)이고, `asActive`가 반환하는 `NULL`은 E-05(상환 완료 → 판정 대상 아님)다. 전자는 시세가 수집되면 값이 생기고, 후자는 영구적이다.

> **구현 방침.** "호출 불가"를 규율이 아니라 타입으로 강제한다. 판정 함수는 `asActive`만 부여할 수 있는 표식이 붙은 입력만 받으므로, 상환 완료 상품에 판정을 시도하는 코드는 컴파일되지 않는다.

### 9.2 E-07 반환 계약 — 평가일이 과거이나 미상환

```
overdueEvaluations(schedules, asOf, redemption)
  = []                                                        if redemption ≠ NULL
  = [ (schedule, daysOverdue) | evaluation_date < asOf ]       otherwise
                                                              (evaluation_date 오름차순)

daysOverdue = asOf − evaluation_date                          (양수)
```

- **상환 완료 상품은 빈 배열이다.** E-05가 우선한다. 상환 처리로 확인이 완결되었으므로 경과 차수를 다시 묻지 않는다.
- 평가일 당일은 경과로 보지 않는다. §7.2의 "다음 도래 평가일"과 경계를 공유한다.
- 경과한 차수를 **전부** 반환한다. 최근 1건만 반환하면 여러 차수가 연속으로 경과한 상품에서 앞 차수의 확인이 누락된다.
- 결과가 비어 있지 않은 상품은 "상환 처리 또는 이월 확인" 대상이다. **시스템이 이월을 자동 확정하지 않는다**(D-04와 같은 취지).
- 확인 이력을 저장하지 않으므로 조회 시마다 재산출된다(RD-06).

**`nextEvaluation`(§7.2)과의 관계.** 두 함수는 같은 평가일 목록을 서로 배타적인 두 구간으로 나눈다.

| 함수 | 대상 구간 | 반환 |
|---|---|---|
| `nextEvaluation` | `evaluation_date ≥ asOf` | 그중 최소 1건, 없으면 `NULL` |
| `overdueEvaluations` | `evaluation_date < asOf` | 전부, 없으면 `[]` |

`nextEvaluation`이 `NULL`이고 `overdueEvaluations`가 비어 있지 않으면 만기까지 전 차수가 경과했음에도 상환 실적이 없는 상태다. 적용 차수를 결정할 수 없으므로 귀속연도(§7.2)와 예상 수령액(§4.1)도 산출되지 않는다.

### 9.3 E-09 반환 계약 — 환율 없음 *(v1.4 · 구현 컷 a2(건수)·a3(환율))*

```
taxableIncomeKrw(e) = null    if e는 달러 상품의 추정 건 ∧ GENERAL ∧ 달러 이익 > 0 ∧ x(USD, asOf) 없음
                                                                              (§4.8 마지막 분기)

F(owner, year)                = Σ taxableIncomeKrw(e)  for e ∈ 그 키의 건, taxableIncomeKrw(e) ≠ null
                              + other_financial_income                        (§7.3)
unconvertedCount(owner, year) = | { e ∈ 그 키의 건 : taxableIncomeKrw(e) = null } |
exchangeRateBasis             = ExchangeRateBasisView (DOC-011 §4.0)   그 결과의 어떤 값이 x로 환산되었으면 — 그 x
                              = null                                   otherwise
excludedForeignCount(Y)       = | { 달러 상품 els : x 없음 ∧ firstNeeded(els) ≤ Y } |   (전망만, 행 Y마다 — §7.5 · DOC-011 §4.7)
firstNeeded(els)              = els가 처음 원화 합(그 해 수령액 · 잔여 원금)에 필요해진 행
                              = 없음                                   if 귀속연도 < Y₀인 상환 (어느 항에도 없다 — 세지 않는다)
```

- **`null`은 0이 아니다.** 0은 「안다 — 과세 대상이 아니거나 이익이 없다」이고 `null`은 「모른다」다. 합은 `null`을 건너뛰고 **센다** — 세지 않고 0으로 흡수하면 E-09가 금지하는 조용한 배제가 된다.
- **예외를 던지지 않는다.** 계산은 줄어든 `F`로 끝까지 진행되고 §5·§6의 세액·보험료도 그 `F`로 나온다. 그 값은 과소 추정이므로 **건수가 그 옆에 있어야 한다**(DOC-008 ST-07). 검산 A-3과 A-4를 겹치면 이유가 보인다 — 환율이 없으면 `F`가 15,000,000으로 기준금액 아래에 보이고 피부양자 보험료 1,659,492원이 0으로 보인다.
- **상품 단위가 아니라 건 단위다.** 확정 원화 과세는 `x`와 무관하게 늘 들어가므로, 같은 상품 안에서 확정 건은 남고 추정 건만 빠진다. 전망의 `F(Y₀)`와 SCR-401의 `F`가 같은 건을 빼는 것이 이 선택의 검증 가능한 형태다(§7.5).
- **세는 단위는 건이다.** 달러 상품당 추정 건이 하나인 동안(컷 b4 이전)은 상품 수와 같다. 월지급 달러 상품이 들어오면 갈리며 화면이 어느 쪽을 말할지는 컷 b1이 정한다(DOC-008 ST-07 ⓑ).
- **`excludedForeignCount`는 행마다 세고 마지막 행까지 센다** — 그 상품이 처음 원화 합에 필요해진 행부터다. 상환 연도에서 멈추면 안 된다: 상환 뒤의 행에서도 `cumulativeNet`·`cumulativeAssets`가 그 상품의 세후 회수를 잃으므로 그 행의 원화 합도 짧은데 개수는 0을 말하게 된다(DOC-011 §4.7). §7.5의 배타 분할에서 전망 구간의 달러 상품은 `Y₀` 행부터 어느 한 항(잔여 원금이거나 그 해·누적 세후 회수)에 있으므로 지금의 모델에서는 `firstNeeded`가 늘 `Y₀`이고 세는 상품은 **모든 행에서 1**이다 — 행마다 다른 값이 나오면 셈이 어느 열을 빠뜨렸다는 신호다.
- **`unconvertedCount > 0`이면 `exchangeRateBasis = null`이다** — 외화가 달러 하나이므로 `x`가 없으면 환산된 값이 없다. 역은 성립하지 않는다: 원화뿐이거나 달러 건이 전부 확정·비과세·이익 ≤ 0이면 `unconvertedCount = 0`이고 기준도 `null`이다.
- **저장하지 않는다.** 조회마다 재산출된다(RD-06과 같은 방식) — 환율이 들어오면(DOC-011 §5.13 수동 입력, 컷 a3 · 자동 수집, 컷 c2) 다음 조회에서 풀린다. 어느 조회가 다시 계산되는지는 DOC-011의 무효화 축이 정한다(DOC-010 AQ-76 — 환율은 세금을 움직이는 첫 공용 입력이다).
- **E-09가 건드리지 않는 것**: 조건 판정(§3 — 비율 비교), 사실 합계(§7.7 — 환산하지 않는다. 원화 환산 합계 줄만 생략된다), §4.5의 달러 기준 참고 원천징수(환율을 쓰지 않는다). 그래서 E-09 상태의 상품은 워스트오브·조건 충족·차수별 참고값·통화별 합계가 정상으로 보이고 **원화로 바꿔야 하는 추정만** 빠진다.
- **필드의 자리**는 DOC-011이다 — §4.1(올해 세금 요약) · §4.3(상품의 예상 과세) · §4.6 · §4.7 · §4.8. 필드 이름과 표 행은 DOC-011이 정하고 코드 커밋에 함께 넣는다.
- **컷 a2에서는 늘 이 상태다** — `exchange_rates`가 없으므로 일반계좌 달러 추정 건은 전부 `null`이고 전망의 달러 상품은 전부 `excludedForeignCount`에 든다. 설계된 상태이며 결함이 아니다(§4.8 「단계」).
